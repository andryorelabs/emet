Cada subcomando do `emet`, a tabela de gates e registros, os códigos de saída e as variáveis de ambiente. Os termos seguem o [GLOSSARY.md](../../GLOSSARY.md). Voltar ao [README](../../README.md). Todo comando imprime seu uso com `--help`.

## Subcomandos

Três comandos de barra envolvem a CLI dentro do Claude Code: `/emet:run` (o pipeline), `/emet:init` (`emet init`) e `/emet:doctor` (`emet doctor .`). No Codex, são as skills `$emet:run`, `$emet:init` e `$emet:doctor`. Um `emet` em um terminal comum exige o `install.sh`; caso contrário, execute `! emet <subcommand>` dentro de uma sessão.

`emet <command> [...args]`. `emet --version` imprime a versão.

### Configuração e auditoria

- `emet migrate [--dry-run]`: renomeia um repositório legado para os nomes do emet.
- `emet init [--tracker linear|github|local] [--after-spec release|promote|none] [--force]`: detecta automaticamente o gerenciador de pacotes, a branch tronco, o tipo de tracker e o modo after-spec (veja [`handoff.afterSpec`](configuration.md#handoff)), define [`schema.ownedPaths`](configuration.md#schema) quando encontra um schema do Prisma (`prisma/schema.prisma` ou uma pasta `prisma/schema/`) ou uma pasta de migrations do Drizzle (`drizzle/` ao lado de um `drizzle.config.*`), e escreve o `emet.config.json` e os arquivos `docs/agents/*.md`. `--tracker local` configura o tracker local.
- `emet doctor [--all] [<path> ...]`: auditoria somente leitura de quantos repositórios você quiser de uma só vez; por padrão, o diretório atual. Para um repositório que configura [`verify.browser`](configuration.md#verify), também informa um achado opcional sobre o `agent-browser`: um binário ausente é `indeterminate` (uma linha `optional:` com o remédio de instalação) e, quando o binário existe, um `agent-browser doctor` que falha aparece como aviso. Nenhum dos dois é jamais um erro, e nenhum altera o código de saída. Um repositório sem `verify.browser` não mostra nada.
- `emet setup [--yes] [--with <ids>] [--list] [--json]`: oferece as instalações opcionais com prompts do readline: `mattpocock-skills` (ligado por padrão), `engram`, `mascot`, `orca-pet`, `gh-auth`, `agent-browser` (desligado por padrão; executa `bun add -g agent-browser@latest` e depois `agent-browser install`, escreve `~/.agent-browser/config.json` com `contentBoundaries: true` e `maxOutput: 50000` somente quando esse arquivo não existe, depois executa `agent-browser doctor` e imprime um aviso se ele falhar; nunca fixa uma versão e nunca passa `--with-deps`, então, quando faltam bibliotecas do sistema, imprime o comando para você executar), `context7` (desligado por padrão; executa `bun add -g ctx7@latest`, depois `ctx7 setup --cli --claude --yes`, e `ctx7 setup --cli --codex --yes` somente quando `codex` está no PATH; instala a CLI `ctx7` e sua skill `find-docs`, não o servidor MCP, nunca fixa uma versão e imprime o comando para executar manualmente quando uma etapa de `ctx7 setup` falha; o `ctx7` envia eventos de uso anônimos, a menos que `CTX7_TELEMETRY_DISABLED=1` esteja definido, e um `CONTEXT7_API_KEY` no ambiente tem precedência sobre a conta salva por `ctx7 login`), `firecrawl-local` (desligado por padrão; requer `cargo`, executa `cargo install firecrawl-local` quando o binário não existe e depois registra um servidor MCP do Claude Code no escopo do usuário com `FIRECRAWL_CLOUD=search` e `--public-only`, substituindo um registro anterior com outras configurações: scrape, crawl e map rodam na máquina, só a busca na web vai para o Firecrawl Cloud e endereços privados são bloqueados. Passa o Chrome mais recente baixado pelo `agent-browser` como `FIRECRAWL_CHROME_PATH`; no Linux, onde o AppArmor restringe namespaces de usuário sem privilégio, imprime um perfil do AppArmor e os comandos `sudo` para carregá-lo, porque o Firecrawl Local nunca executa o Chrome sem seu sandbox. Sem um Chrome utilizável, páginas renderizadas com JavaScript voltam vazias) e as configurações recomendadas do Claude Code (`claude-settings`, aplicadas só quando escolhidas, após um backup com timestamp do `settings.json`). Sem TTY, ou com `--yes` ou `--with`, não pergunta nada e instala exatamente os itens nomeados; sem TTY e sem `--with` não instala nada e imprime o catálogo de `--list`. Cada etapa informa `installed`, `already-present`, `skipped` ou `failed`; uma falha não interrompe as demais, e o código de saída é 1 se alguma falhou. `/emet:setup` é a entrada do plugin e faz as mesmas perguntas com `AskUserQuestion`.
- `emet fleet list [--root <dir>] [--json]`: lista os repositórios git com um `emet.config.json` um nível abaixo de `--root` (padrão `~/code`), com `tracker.kind`, `handoff.autoChain` e `models.worker`. `emet fleet set <key> <value> [--root <dir>] [--dry-run]` altera uma chave de configuração em cada repositório listado, validando antes pelo carregador de configuração (um valor inválido não altera nada e sai com 1). `emet fleet launch --feature <text> [--root <dir>] [--repos <a,b>] [--dry-run]` abre uma sessão `/emet:run --draft <text>` em cada repositório após as verificações de prontidão do `emet chain`. `[--dry-run]` imprime os lançamentos planejados sem iniciar uma sessão. Veja o [guia de fleet](../guide/fleet.md).
- `emet preflight [--run <id>] [--post-dispatch]`: confirma que o repositório está pronto para despachar.
- `emet skill-path <name>`: imprime o caminho absoluto do `SKILL.md` de uma skill do mattpocock-skills. Termina com código 1 se a skill não for encontrada.
- `emet selftest`: executa os testes unitários da própria CLI. Somente em instalações a partir do código-fonte; um binário compilado termina com código 1 e manda você executar `emet doctor`.

Em qualquer repositório git:

```bash
emet init          # autodetects package manager, trunk branch, tracker kind
emet preflight      # confirms the repo is dispatch-ready
```

O `emet init` deixa um marcador `TODO(emet):` nos arquivos `docs/agents/*.md` gerados para tudo o que ele não consegue inferir sozinho (um lock compartilhado do banco de dados de testes, a propriedade do schema e assim por diante). Preencha-os; o `emet preflight` se recusa a despachar enquanto restar algum.

Depois, dentro do Claude Code (no Codex, use `$emet:run` com os mesmos argumentos):

```text
/emet:run <describe the feature>              # interview → wave 1; later waves via --dispatch/autoChain
/emet:run --draft <describe the feature>      # stop after tickets are created
/emet:run --dispatch <spec-id>                # dispatch a --draft'd spec later
```

#### Verificação de frota

O `emet doctor` audita vários repositórios de uma só vez, somente leitura:

```bash
emet doctor ~/code/*
```

Informa, por repositório: um `emet.config.json` válido, os quatro arquivos `docs/agents/*.md` presentes, zero marcadores `TODO(emet):` restantes, se os comandos de `commands.selfCheck` realmente são resolvidos e os achados de dependências específicos do tracker daquele repositório (`gh`, Linear; veja [dependências](dependencies.md#o-que-verifica-o-quê)). O plugin mattpocock-skills e as flags das CLIs externas (`gh`, mais as do host de agente: `claude --bg` e `claude agents --json` no Claude Code, `codex exec --json` e `--output-schema` no Codex, verificadas via `--help`) são checados uma única vez para toda a varredura, não por repositório.

### Execuções, workers e slots

- `emet claims --reserve <ticket> --run <id> --anchor <pid>`: reserva um ticket para uma execução. `--release <ticket>`, `--list` e `--prune [--dry-run]` liberam uma reivindicação, listam as reivindicações ou removem as obsoletas.
- `emet slots --acquire --run <id> --anchor <pid> --ticket <ticket>`: pega um slot de worker do pool de todo o host em `~/.local/state/emet/slots`. `--release --run <id>`, `--release-index <index>` e `--list` liberam slots ou os listam.
- `emet cleanup [--run <id> | --all] [--dry-run] [--force]`: sem argumentos, recupera execuções encerradas ou mortas cujo trabalho já aterrissou; `--run` limpa esta execução; `--all` é uma varredura de branches em todo o repositório. Depois de um merge, `emet cleanup --run <runId>` libera as branches, as reivindicações de tickets e os slots de workers da onda. Em todos os modos ele também exclui cada branch local cujo PR foi mesclado no commit da ponta da branch, junto com o worktree de agente limpo e desbloqueado que a contém.
- `emet lock-reason --run <id> --ticket <ticket> [--anchor <pid>]`: imprime o motivo do `git worktree lock` que um worker escreve no bootstrap.
- `emet launch <spec-id> --wave <n>`: no Claude Code, inicia uma onda como uma sessão `claude --bg` e abre sua aba do Orca conforme `handoff.launcher` (no Codex, veja [Host Codex](#host-codex)). Faz o lançamento completo (verificação de sessão duplicada, `claude --bg`, aba) e imprime `{ name, id, attach, orcaTab: { opened, reason } }`. Use-o, e não um `claude --bg` solto, sempre que quiser uma onda em outra sessão manualmente.
- `emet chain --ticket <id> --spec <id> --wave <n> [gate flags]`: executa `emet gate` com os flags do gate recebidos e só inicia a próxima onda quando a decisão é `chain`. Antes de lançar, verifica a prontidão (folga de memória do host, disco e inodes livres no repositório e em `/tmp`, a CLI `orca`) e depois confirma que a sessão filha aparece na listagem. Qualquer outra decisão, um problema de prontidão bloqueante (`low-memory`, `low-disk`, `low-inodes`, `orca-unavailable`) ou uma sessão existente para a mesma especificação e onda termina com saída 1 com os motivos e não lança nada.
- `emet status [--spec <id>] [--brief]`: Working / Checking / Ready / Needs-decision por onda como JSON mais uma linha de resumo. `--brief` imprime no máximo três linhas: o estado geral, o que está esperando uma pessoa (se houver) e a próxima ação. `emet status --help` documenta o JSON.
- `emet run current [--json]`: imprime a execução ativa do repositório (id da execução, spec, onda, fase e última atualização), lida de `.emet/phase.json`. Sem execução ativa, imprime `no active run` e sai com 0.
- `emet insights [--since <iso|7d|30d>] [--repo <path>] [--all] [--json] [--mark-baseline]`: lê o [diário de eventos](../guide/journal.md) e informa execuções por origem (humana ou auto), decisões do gate por decisão e motivo, intervenções humanas por execução, resultados de lançamento e tickets fechados. Linhas ilegíveis são ignoradas e contadas. `--mark-baseline` acrescenta uma linha de base; relatórios seguintes cobrem apenas eventos posteriores a ela, a menos que `--all` seja usado. Um diário vazio ou ausente imprime um relatório zerado e sai com 0.
- `emet usage [--session <id> | --file <path>] [--stalled [--minutes N]] [--project-dir <path>]`: informa o uso da sessão; `--stalled` lista workers travados.
- `emet handoff --check <path> [--expect-skills a,b] | --render <path>`: valida ou renderiza a nota `.emet/handoff-<ticket>.md` de um worker. A nota pode conter uma seção `skills:`, escrita como `skills: none` ou `skills: loaded: a, b; missing: c`; ela é obrigatória apenas quando `state` é `done`, e qualquer outro valor reprova a verificação. `--expect-skills a,b` (somente com check) reprova a verificação para cada skill nomeada que não esteja nem na lista `loaded` nem na lista `missing`. Uma verificação aprovada imprime `missing skills: …` quando a lista `missing` não está vazia.
- `emet metrics [--run <id>]`: informa tokens, custo equivalente em API e tempo de relógio por ticket, por onda e por execução, lidos das transcrições de sessão. Também compara o orçamento de contexto estimado por ticket com o que cada worker realmente usou. Seu resumo vai no final do relatório final da execução.

### Planejamento, revisão e aterrissagem

- `emet promote --spec <id> [--dry-run] [--no-promote] [--hold]`: a etapa after-spec, conforme [`handoff.afterSpec`](configuration.md#handoff). No modo `promote`, abre um pull request de `develop` para `main` com o título `chore: 🔖 promote develop`, espera com `emet ci --pr <n> --wait`, faz o merge com um commit de merge só quando o estado é `pass`, e então, apenas se `develop` estiver atrás de `main`, abre um pull request de sincronização de `main` para `develop`, espera pelos checks dele do mesmo modo e faz o merge com um commit de merge só quando o estado é `pass`; um pull request de sincronização cujo estado é `fail`, `timeout` ou `env-fault`, ou cujo merge é rejeitado, permanece aberto e nunca altera o resultado do promote. Acrescenta ao diário um evento `promote` com o número do pull request, `merged`, `syncPrNumber`, `syncMerged`, `syncReason`, `rule` e `reason`. `afterSpec` pode ser uma lista de regras; o modo é então escolhido a partir dos caminhos que promover `develop` traria (veja [`handoff.afterSpec`](configuration.md#handoff)), e um `git fetch` ou `git diff` que falhe faz o comando sair com 1 antes de abrir qualquer pull request. O resultado impresso traz `rule` (o índice da regra correspondente, ou `null` para a forma em string ou sem correspondência), `reason`, `syncPrNumber` (`null` quando nenhum pull request de sincronização foi aberto), `syncMerged` e `syncReason` (uma frase que diz por que um pull request de sincronização ficou aberto, senão `null`) e `deployCheck: { run, reason }`, que informa se o coordenador deve executar `emet deploy-check`. No modo `release`, não faz merge de nada e deixa o pull request de release para uma pessoa. Com `afterSpec` `none`, com `--no-promote`, ou quando a última onda da spec foi deixada aberta ou sinalizada, sai com 0 e uma nota `skipped`; ainda assim ele roda após uma última onda limpa, para que o resultado traga a decisão `deployCheck` (no trunk `main` o deploy check roda qualquer que seja o modo). Um CI diferente de `pass` não faz merge de nada e sai com 1. `--dry-run` não abre nenhum pull request. `emet promote --spec <id> --hold` grava o marcador `<run dir>/runs/<id>/no-promote` e imprime `{"held":true}`; enquanto ele existir, `emet promote --spec <id>` sai com 0 e uma nota `skipped` sem abrir nenhum pull request, de modo que `--no-promote` persiste entre as sessões de uma especificação.
- `emet deploy-check [--json]`: executa `deploy.check.command` até sair com 0, em até `retries` tentativas ou `timeoutSeconds`, esperando `intervalSeconds` entre elas, e imprime `state: ok | failed | timeout` com `attempts`. Saída `0` ok, `1` failed, `3` timeout. Sem `deploy.check` configurado, sai com 0 e `skipped: "no deploy check configured"`. O coordenador o executa somente quando o resultado de `emet promote` tem `deployCheck.run` true. Veja [`deploy`](configuration.md#deploy).
- `emet validate --spec <id> | --file <path>`: validação do plano; veja [Gates e registros](#gates-e-registros).
- `emet surfaces --check <file.json | ->`: rejeita globs de superfícies permitidas que se sobreponham entre os tickets de uma onda.
- `emet approve --run <id>`, `emet materialize-log`, `emet results`, `emet verify`, `emet review-package`, `emet review`, `emet gate`: veja [Gates e registros](#gates-e-registros).
- `emet assess --base <ref> --head <ref>`: classifica um diff como `passive`, `medium` ou `high` e imprime JSON com o nível, os motivos e o modelo e esforço recomendados para o revisor, além de `browserVerify: { run, reason }`: `run` é `true` somente quando o nível tem revisor, [`verify.browser`](configuration.md#verify) está configurado, o binário `agent-browser` está no PATH e, quando `paths` está definido, um caminho alterado corresponde; caso contrário, `reason` nomeia a primeira condição que falhou. Também imprime `dualReview: { run, reason }`: `run` é `true` apenas quando o nível é `high`, `agentHost` é `claude`, [`review.dual`](configuration.md#review) não é `off` e o binário `codex` está no PATH; caso contrário, `reason` nomeia a primeira condição que falhou. Com `--quick`, o JSON inclui também `"quickRejected": true|false` e o comando sai com código 1 quando o nível é `high` (um **Stop** para uma **Quick run**: sem merge automático, o PR continua aberto) e com 0 caso contrário; sem `--quick` a saída e os códigos de saída não mudam. Veja [Models & effort](../../README.md#models--effort) e [`review`](configuration.md#review).
- `emet land --spec <s> --branch <integration> --tickets <id,...>`: mescla uma branch de integração no tronco local (`landing.mode` `merge`). `commands.selfCheck` faz as vezes da CI e nada é enviado com push.
- `emet spec-branch ensure|integrate|status|sync|land|abandon --spec <id>`: a branch do spec `spec/<id>` de `landing.unit: spec` (veja [`landing`](configuration.md#landing)). Todos imprimem JSON. `ensure` cria a branch a partir do tronco (idempotente), grava `.emet/specs/<id>/branch.json` e se recusa quando a branch de outro spec está em checkout. `integrate --wave <n> --branch <integration> --tickets a,b` mescla a branch da onda em `spec/<id>` com `--no-ff` e os trailers `Emet-Wave` e `Emet-Tickets`, registra a onda, acrescenta `spec.integrate` e, quando `landing.pushSpecBranch` é true, faz push da branch sem abrir um PR. `status` imprime `branch`, `tip`, as ondas e tickets integrados e `behindTrunk`, e reconstrói `branch.json` a partir dos trailers quando falta uma onda. `sync` mescla o tronco na branch, nunca faz rebase e, em caso de conflito, aborta, lista os caminhos e sai com código diferente de zero. `land [--partial]` faz o sync e, no modo `pr`, faz push da branch, abre um PR com uma linha `Closes` por ticket, espera os checks dele e mescla com `landing.specMergeMethod` (um commit de merge por padrão, ignorando `pr.mergeMethod`); no modo `merge`, mescla no tronco local com `--no-ff` e nunca faz push; acrescenta `spec.land`. `abandon --force` marca `abandoned/spec-<id>` com tag, exclui a branch, acrescenta `spec.abandon` e volta os tickets integrados de um tracker local para `ready-for-agent`; sem `--force` ele se recusa. `emet tracker frontier` conta os tickets listados em `branch.json` como bloqueadores fechados, e `emet status` ganha `specBranch` (`branch`, `tip`, `integratedWaves`).
- `emet spec-merge --spec <id>`: mescla os deltas de requisitos `ADDED`/`MODIFIED`/`REMOVED` da spec em `docs/specs/<area>.md` (`specs.dir`). Com `specs.enabled` ativado, o coordenador escreve os deltas e o executa uma vez por spec, na branch de integração da última onda antes da revisão, e depois faz o commit do resultado. `--deltas-dir` imprime o diretório onde os deltas ficam. Verifica todas as áreas antes de escrever qualquer coisa. Um conflito, ou um requisito que perderia um cenário, termina com código 1 e deixa todos os arquivos intactos. Com `specs.enabled` desativado, não mescla nada e termina com código 0.
- `emet map [--refresh]`: escreve um resumo de uma base de código existente (stack, estrutura, convenções, testes, pontos quentes) em `docs/agents/codebase.md` (`map.path`), carimbado com o SHA do commit a partir do qual foi gerado. O mesmo commit sempre produz o mesmo arquivo. `emet map --stale` termina com código 1 quando o HEAD passou do carimbo, e o `emet preflight` avisa nesse caso. `emet map --for <globs>` imprime apenas as seções que correspondem às superfícies de edição de um ticket; essa saída é a única parte do mapa que o brief de um worker inclui.
- `emet tracker create-spec|create-ticket|read|frontier|set-state|comment|close`: o tracker local sobre `.scratch/`, JSON no stdout. Veja [Tracker local](#tracker-local).
- `emet guard`: o hook `PreToolUse` do Claude Code; lê o JSON do hook no stdin (a forma do Codex está em [Host Codex](#host-codex)). O `install.sh` o conecta em `~/.claude/settings.json`. Bloqueia um punhado de gatilhos conhecidos de falhas em execuções sem supervisão (veja `emet/src/guard.ts`).

### Tracker local

Com `tracker.kind: "local"`, specs e tickets são arquivos markdown em `.scratch/` do worktree principal (sem versionamento): `.scratch/<slug>/spec.md` e `.scratch/<slug>/issues/<NN>-<slug>.md`, cada um com linhas `Status:` e `Blocked by:` e comentários em `## Comments`. O coordenador os lê e escreve por meio de `emet tracker` (`create-spec`, `create-ticket`, `read`, `frontier`, `set-state`, `comment`, `close`). `emet init --tracker local` configura isso. Veja o [ADR-0011](../adr/0011-local-tracker-scratch-convention.md).

`landing.mode` é `"pr"` (padrão) ou `"merge"`, independente do tracker. No modo `merge`, uma onda aterrissa como um único merge local no tronco com `emet land`, com `commands.selfCheck` no lugar da CI e sem push. Com `landing.unit: "spec"` (padrão), o spec inteiro aterrissa uma única vez por meio de `emet spec-branch land`. O `gh` só é obrigatório quando o tracker é `github` ou a aterrissagem é `pr`. Veja o [ADR-0010](../adr/0010-local-merge-landing.md) e [`landing`](configuration.md#landing).

### PRs de aterrissagem e encadeamento de ondas

Com `landing.unit: "wave"`, uma onda é um PR; com `"spec"`, um PR cobre todas as ondas integradas. Seu corpo traz uma linha `Closes #N` para cada ticket (a palavra-chave de fechamento do tracker), e o coordenador move os tickets para em revisão ao abrir o PR. Em seguida o PR é mesclado conforme `pr.autoMerge`, ou deixado aberto quando a onda foi sinalizada, `autoMerge` é `false` ou as correções de CI se esgotaram (o PR então recebe o rótulo de decisão humana). As ondas seguintes rodam em suas próprias sessões, nunca na que executou a onda 1. As seções `pr` e `handoff` controlam o que acontece em seguida; veja [`pr`](configuration.md#pr) e [`handoff`](configuration.md#handoff).

`emet ci --pr <n> --wait [--rerun-flakes] [--timeout-minutes <m>]` consulta os checks do PR até terminarem ou o tempo limite (padrão 30) passar. Com `--rerun-flakes`, reexecuta uma vez cada check com falha por meio de `gh run rerun --failed`; um check que passa na reexecução é um Flake. Imprime `state: pass | fail | env-fault | timeout`, os checks com falha e `flakeReruns`, e nunca faz merge. Um PR sem checks é `pass` com `noChecks: true`. Saída `0` pass, `1` fail ou env-fault, `3` timeout. `env-fault` indica checks que terminaram em `STARTUP_FAILURE` ou ficaram na fila por tempo demais: uma CI que nunca rodou, não uma falha de código.

Com `tracker.kind: "github"`, `emet tracker close <ticket>... [--pr <n>]` fecha cada ticket (`CLA-<n>`, `#<n>` ou um número simples) com `gh issue close --reason completed`, verifica seu estado e informa `closed` ou `already-closed`. `--pr` adiciona o comentário "Landed in #<n>". Depois de processar os tickets, lê o spec issue pai de cada ticket fechado (`gh issue view <n> --json parent`) e, quando `subIssuesSummary` mostra todos os sub-issues concluídos, fecha esse spec como concluído com o comentário "All <total> tickets landed." e o informa em `specs` como `closed`, `open`, `already-closed` ou `failed`; uma falha ao ler ou fechar um spec também sai com `1`. Sai com `1` se algum ticket falhou, depois de processar os demais. Os tickets do Linear são confirmados como Done pelo coordenador por meio do MCP do Linear.

### Host Codex

Estes comandos atendem o host de agente Codex (`agentHost` `"codex"`); veja o [guia do Codex](../guide/codex.md).

- `emet dispatch --role worker --run <id> --ticket <id> --prompt-file <file> [--model <m>] [--effort <e>] [--root <dir>]`: depois de verificar a reserva e o slot, cria `.emet/worktrees/agent-<ticket>`, monta uma camada `CODEX_HOME` por execução e inicia o worker como um `codex exec` desacoplado. `emet dispatch --wait --run <id> --ticket <id> [--timeout <s>]` espera o término e imprime o status de resultado registrado.
- `emet review-run --run <id> --ticket <id> --package <file> --tier <medium|high|passive> [--browser-verify true|false]`: executa o revisor como um `codex exec` somente leitura sobre um pacote do `emet review-package` e imprime o JSON de achados para `emet review --findings`. O nível `passive` não inicia nenhum processo. `--browser-verify` tem padrão `false`; com `true` o prompt termina com o eixo Browser, com `--session review-<run>` preenchido a partir de `--run`, de modo que o revisor Codex verifica a UI como o revisor Claude faz (passe-o quando `emet assess` imprimiu `browserVerify.run: true`; veja [`verify`](configuration.md#verify)). Sem a flag o prompt não muda, e um valor diferente de `true` ou `false` sai com 2 e a linha de uso. `--coverage-out <file>` grava também os Coverage verdicts do revisor Codex em `<file>` como um array JSON (o stdout continua imprimindo apenas os achados); use-o no host Codex, onde um único revisor é executado. Os achados podem incluir os campos opcionais `s` e `userOption` descritos em `emet review`.
- `emet launch <spec-id> --wave <n>`: neste host, inicia um `codex exec` desacoplado que executa `$emet:run --dispatch <spec>` e registra seu id de thread. Nenhuma aba do Orca é aberta, e `codex exec resume <id>` continua a sessão.
- `emet guard`: com `EMET_AGENT_HOST=codex` lê a entrada de hooks do Codex, confere os caminhos de `apply_patch` contra `.emet/surface.json` e mantém o portão de aprovação fechado até uma linha de prompt `approve <id>`.

## Códigos de saída

Os códigos de saída têm o mesmo significado em todos os subcomandos.

| Código | Significado                                                                                           |
| ------ | ----------------------------------------------------------------------------------------------------- |
| `0`    | Limpo.                                                                                                |
| `1`    | Achados sobre os quais agir.                                                                          |
| `2`    | Erro de configuração ou de uso; a ferramenta nunca chegou a executar. Também um comando desconhecido. |
| `3`    | Erro interno.                                                                                         |

Uma flag desconhecida também sai com `2` e nomeia a flag. Ctrl-C sai com `130`.

## Flags globais

Todo comando as aceita; as flags próprias de cada comando são listadas por `emet <command> --help`.

| Flag         | Efeito                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| `--json`     | Imprime um único envelope `{ok, data, error: {code, message, fix}}` no stdout, inclusive para `--help` e `--version`. |
| `--no-color` | Desativa a cor ANSI. A cor também respeita `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb` e se a saída é um TTY.              |
| `--verbose`  | Imprime a pilha de um erro inesperado. Sem ela, o catch de nível superior imprime um erro de uma linha.               |
| `--help`     | Imprime o uso do comando.                                                                                             |

`emet --version` imprime a versão; `emet --version --json` imprime `{"ok": true, "data": {"version": ...}, "error": null}`. Sob `--json`, um comando que falha sai com seu código habitual e imprime `ok: false` com um `code` de erro entre `findings`, `usage`, `internal`, `slice-timeout`, `expired`, `bad-range` ou `exit-<n>`; o que o comando imprimiu no stdout é o `data` do envelope.

Em um TTY, `emet` imprime um aviso de uma linha no stderr quando uma versão mais recente é conhecida. Ele verifica no máximo uma vez por dia, guarda a resposta em cache, nunca espera pela rede e fica em silêncio sob `--json` ou sem TTY.

## Variáveis de ambiente

Variáveis voltadas ao usuário. Uma variável, quando definida, substitui o valor de configuração correspondente.

| Variável                      | Efeito                                                                                                                                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `EMET_SKIP_DEPENDENCY_CHECKS` | `EMET_SKIP_DEPENDENCY_CHECKS=1 emet preflight` rebaixa um bloqueio por dependências a um aviso apenas naquela execução. Defina-a no seu próprio shell, não em nada que o coordenador execute sem supervisão. |
| `EMET_MAX_LIVE_WORKERS`       | Substitui [`concurrency.maxLiveWorkers`](configuration.md#concurrency); aceita um inteiro positivo ou `auto`.                                                                                                |
| `EMET_RUN_IDLE_THRESHOLD_MS`  | Substitui [`concurrency.runIdleThresholdMs`](configuration.md#concurrency), em milissegundos.                                                                                                                |
| `EMET_STATE_DIR`              | Diretório de estado de todo o host, que guarda o pool de slots de workers. Ordem de resolução: `$EMET_STATE_DIR`, depois `$XDG_STATE_HOME/emet`, depois `~/.local/state/emet`.                               |
| `EMET_MEM_RESERVE_GIB`        | Folga de memória em GiB que deve continuar livre; uma aquisição é negada quando a memória disponível está abaixo disso. Padrão 8. Também alimenta o limite `auto` de workers.                                |
| `EMET_MEM_PER_WORKER_GIB`     | Memória em GiB presumida por worker quando `maxLiveWorkers` é `auto`. Padrão 2. Aumente para um stack mais pesado por worker, como uma suíte E2E com navegador por worktree.                                 |
| `EMET_CPU_OVERSUBSCRIBE`      | Multiplicador de CPU para o limite `auto` de workers. Padrão 1.                                                                                                                                              |
| `EMET_AGENT_HOST`             | `codex` faz o `emet guard` ler a entrada de hooks do Codex. É definida pelos hooks do Codex; deixe sem definir no Claude Code.                                                                               |

O limite `auto` é `clamp(min(cpuCount × EMET_CPU_OVERSUBSCRIBE, floor((memTotal − EMET_MEM_RESERVE_GIB) / EMET_MEM_PER_WORKER_GIB)), min, max)`. Os nomes legados `FORGE_*` ainda são lidos; `EMET_*` vence quando ambos estão definidos.
