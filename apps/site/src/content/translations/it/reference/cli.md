Ogni sottocomando di `emet`, la tabella di gate e registri, i codici di uscita e le variabili d'ambiente. I termini seguono [GLOSSARY.md](../../GLOSSARY.md). Torna al [README](../../README.md). Ogni comando stampa il proprio utilizzo con `--help`.

## Sottocomandi

Tre comandi slash racchiudono la CLI dentro Claude Code: `/emet:run` (la pipeline), `/emet:init` (`emet init`) e `/emet:doctor` (`emet doctor .`). Su Codex sono le skill `$emet:run`, `$emet:init` e `$emet:doctor`. Un `emet` in un normale terminale richiede `install.sh`; altrimenti esegui `! emet <subcommand>` all'interno di una sessione.

`emet <command> [...args]`. `emet --version` stampa la versione.

### Configurazione e verifica

- `emet migrate [--dry-run]`: rinomina un repo legacy con i nomi di emet.
- `emet init [--tracker linear|github|local] [--after-spec release|promote|none] [--force]`: rileva automaticamente gestore di pacchetti, branch trunk, tipo di tracker e modalità after-spec (vedi [`handoff.afterSpec`](configuration.md#handoff)), imposta [`schema.ownedPaths`](configuration.md#schema) quando trova uno schema Prisma (`prisma/schema.prisma` o una cartella `prisma/schema/`) o una cartella di migrazioni Drizzle (`drizzle/` accanto a un `drizzle.config.*`), e scrive `emet.config.json` e i file `docs/agents/*.md`. `--tracker local` configura il tracker locale.
- `emet doctor [--all] [<path> ...]`: verifica in sola lettura di un numero qualsiasi di repo in una volta; per impostazione predefinita la directory corrente. Per un repo che configura [`verify.browser`](configuration.md#verify) riporta anche un riscontro facoltativo su `agent-browser`: un binario mancante è `indeterminate` (una riga `optional:` con il rimedio di installazione), e quando il binario esiste un `agent-browser doctor` che fallisce compare come avviso. Nessuno dei due è mai un errore e nessuno cambia il codice di uscita. Un repo senza `verify.browser` non mostra nulla.
- `emet setup [--yes] [--with <ids>] [--list] [--json]`: propone le installazioni opzionali con prompt readline: `mattpocock-skills` (attivo di default), `engram`, `mascot`, `orca-pet`, `gh-auth`, `agent-browser` (spento di default; esegue `bun add -g agent-browser@latest` poi `agent-browser install`, scrive `~/.agent-browser/config.json` con `contentBoundaries: true` e `maxOutput: 50000` solo quando quel file non esiste, poi esegue `agent-browser doctor` e stampa un avviso se fallisce; non fissa mai una versione e non passa mai `--with-deps`, quindi quando mancano librerie di sistema stampa il comando da eseguire a mano), `context7` (spento di default; esegue `bun add -g ctx7@latest`, poi `ctx7 setup --cli --claude --yes`, e `ctx7 setup --cli --codex --yes` solo quando `codex` è nel PATH; installa la CLI `ctx7` e la sua skill `find-docs`, non il server MCP, non fissa mai una versione e stampa il comando da eseguire a mano quando un passo di `ctx7 setup` fallisce; `ctx7` invia eventi di utilizzo anonimi a meno che non sia impostato `CTX7_TELEMETRY_DISABLED=1`, e un `CONTEXT7_API_KEY` nell'ambiente ha la precedenza sull'account salvato da `ctx7 login`), `firecrawl-local` (spento di default; richiede `cargo`, esegue `cargo install firecrawl-local` quando il binario manca, poi registra un server MCP di Claude Code a livello utente con `FIRECRAWL_CLOUD=search` e `--public-only`, sostituendo una registrazione precedente con altre impostazioni: scrape, crawl e map girano sulla macchina, solo la ricerca web va a Firecrawl Cloud e gli indirizzi privati sono bloccati. Passa il Chrome più recente scaricato da `agent-browser` come `FIRECRAWL_CHROME_PATH`; su Linux, dove AppArmor limita i namespace utente non privilegiati, stampa un profilo AppArmor e i comandi `sudo` per caricarlo, perché Firecrawl Local non esegue mai Chrome senza la sua sandbox. Senza un Chrome utilizzabile, le pagine che si renderizzano con JavaScript tornano vuote) e le impostazioni consigliate di Claude Code (`claude-settings`, applicate solo se scelte, dopo un backup con timestamp di `settings.json`). Senza TTY, o con `--yes` o `--with`, non chiede nulla e installa esattamente gli elementi indicati; senza TTY e senza `--with` non installa nulla e stampa il catalogo di `--list`. Ogni passo riporta `installed`, `already-present`, `skipped` o `failed`; un errore non ferma gli altri, e il codice di uscita è 1 se qualcuno è fallito. `/emet:setup` è il punto di ingresso del plugin e pone le stesse scelte con `AskUserQuestion`.
- `emet fleet list [--root <dir>] [--json]`: elenca i repo git con un `emet.config.json` un livello sotto `--root` (predefinito `~/code`), con `tracker.kind`, `handoff.autoChain` e `models.worker`. `emet fleet set <key> <value> [--root <dir>] [--dry-run]` modifica una chiave di configurazione in ogni repo elencato, validando prima tramite il caricatore di configurazione (un valore non valido non cambia nulla ed esce con 1). `emet fleet launch --feature <text> [--root <dir>] [--repos <a,b>] [--dry-run]` apre una sessione `/emet:run --draft <text>` in ogni repo dopo i controlli di prontezza di `emet chain`. `[--dry-run]` stampa i lanci pianificati senza avviare alcuna sessione. `emet fleet status [--json]` legge il journal globale e stampa, per ogni repo, l'ultimo stato di ogni sessione nelle ultime 24 ore (esclusa `ended`). Con `--json` stampa `{ repos: [{ repo, sessions: [{ sessionId, state, blocked, since, runId }] }], blocked: <count> }`; altrimenti una riga per repo, `<repo>: <b> blocked, <w> working, <i> idle`, con i repo bloccati per primi. Esce con 0 anche quando è vuoto. Vedi la [guida fleet](../guide/fleet.md).
- `emet preflight [--run <id>] [--post-dispatch]`: conferma che il repo è pronto per il dispatch.
- `emet skill-path <name>`: stampa il percorso assoluto di `SKILL.md` di una skill di mattpocock-skills. Esce con 1 se la skill non viene trovata.
- `emet selftest`: esegue i test unitari della CLI stessa. Solo per installazioni da sorgenti; un binario compilato esce con 1 e ti dice di eseguire `emet doctor`.

In qualsiasi repo git:

```bash
emet init          # autodetects package manager, trunk branch, tracker kind
emet preflight      # confirms the repo is dispatch-ready
```

`emet init` lascia un marcatore `TODO(emet):` nei file `docs/agents/*.md` generati per tutto ciò che non riesce a dedurre da solo (un lock condiviso del database di test, la proprietà dello schema e così via). Compilali; `emet preflight` rifiuta il dispatch finché ne resta uno.

Poi, dentro Claude Code (su Codex usa `$emet:run` con gli stessi argomenti):

```text
/emet:run <describe the feature>              # interview → wave 1; later waves via --dispatch/autoChain
/emet:run --draft <describe the feature>      # stop after tickets are created
/emet:run --dispatch <spec-id>                # dispatch a --draft'd spec later
```

#### Controllo della flotta

`emet doctor` controlla più repo in una volta, in sola lettura:

```bash
emet doctor ~/code/*
```

Per ogni repo il report indica: un `emet.config.json` valido, tutti e quattro i file `docs/agents/*.md` presenti, nessun marcatore `TODO(emet):` rimasto, se i comandi in `commands.selfCheck` si risolvono davvero e i risultati sulle dipendenze specifiche del tracker del repo (`gh`, Linear; vedi [dipendenze](dependencies.md#cosa-controlla-cosa)). Il plugin mattpocock-skills e i flag delle CLI esterne (`gh`, più quelli dell'Agent host: `claude --bg` e `claude agents --json` su Claude Code, `codex exec --json` e `--output-schema` su Codex, verificati tramite `--help`) vengono controllati una sola volta per l'intera scansione, non per ogni repo.

### Esecuzioni, worker e slot

- `emet claims --reserve <ticket> --run <id> --anchor <pid>`: riserva un ticket per un'esecuzione. `--release <ticket>`, `--list` e `--prune [--dry-run]` rilasciano un claim, elencano i claim o eliminano quelli obsoleti.
- `emet slots --acquire --run <id> --anchor <pid> --ticket <ticket>`: prende uno slot worker dal pool dell'host in `~/.local/state/emet/slots`. `--release --run <id>`, `--release-index <index>` e `--list` liberano gli slot o li elencano.
- `emet cleanup [--run <id> | --all] [--dry-run] [--force]`: senza argomenti, recupera le esecuzioni chiuse o morte il cui lavoro è atterrato; `--run` pulisce questa esecuzione; `--all` è una scansione dei branch su tutto il repo. Dopo un merge, `emet cleanup --run <runId>` libera i branch, i claim dei ticket e gli slot dei worker dell'ondata. In ogni modalità elimina anche ogni branch locale la cui PR è stata unita al commit di testa del branch, insieme al worktree dell'agente pulito e non bloccato che lo contiene.
- `emet lock-reason --run <id> --ticket <ticket> [--anchor <pid>]`: stampa il motivo del `git worktree lock` che un worker scrive al bootstrap.
- `emet launch <spec-id> --wave <n>`: su Claude Code, avvia un'ondata come sessione `claude --bg` e ne apre la scheda di Orca secondo `handoff.launcher` (su Codex vedi [Host Codex](#host-codex)). Esegue l'intero avvio (controllo delle sessioni duplicate, `claude --bg`, scheda) e stampa `{ name, id, attach, orcaTab: { opened, reason } }`. Usalo, e non un semplice `claude --bg`, ogni volta che vuoi un'ondata in un'altra sessione a mano.
- `emet chain --ticket <id> --spec <id> --wave <n> [gate flags]`: esegue `emet gate` con i flag del gate ricevuti e avvia l'ondata successiva solo quando la decisione è `chain`. Prima del lancio controlla la prontezza (margine di memoria dell'host, disco e inode liberi nel repo e in `/tmp`, la CLI `orca`) e poi conferma che la sessione figlia sia elencata. Qualsiasi altra decisione, un problema di prontezza bloccante (`low-memory`, `low-disk`, `low-inodes`, `orca-unavailable`) o una sessione già esistente per la stessa specifica e ondata termina con codice 1 indicando i motivi e non lancia nulla.
- `emet status [--spec <id>] [--brief]`: Working / Checking / Ready / Needs-decision per ondata come JSON più una riga di riepilogo. `--brief` stampa invece al massimo tre righe: lo stato complessivo, ciò che attende una persona (se c'è) e l'azione successiva. `emet status --help` documenta il JSON. Il JSON include `sessions[]` con `{ sessionId, state, blocked, since, runId }` per l'ultimo evento `session.attention` di ogni sessione di questo repo nelle ultime 24 ore (esclusa `ended`); `blocked` è `true` quando `state` è `needs-decision`. Una sessione bloccata rende `needs-decision` lo stato complessivo anche senza ondata, la riga di riepilogo indica quante sono bloccate e `--brief` le elenca nella riga di ciò che attende una persona.
- `emet run current [--json]`: stampa l'esecuzione attiva del repo (id esecuzione, spec, ondata, fase e ultimo aggiornamento), letta da `.emet/phase.json`. Senza esecuzione attiva stampa `no active run` ed esce con 0.
- `emet memory search --json <query> [--limit <n>]`: cerca in [Engram](https://github.com/Gentleman-Programming/engram) le lezioni delle esecuzioni precedenti. Cerca con `match_mode: "any"` (`--limit` è 5 per impostazione predefinita, massimo 20), conserva solo le note la cui topic key inizia con `emet/<repo>/lessons/` e stampa `{available: true, results: [{id, topicKey, title, content}]}` con `content` troncato a 2000 caratteri. `<repo>` è l'ultimo segmento del percorso di `git remote get-url <repo.remote>` senza `.git`, altrimenti il basename del worktree principale.
- `emet memory save --json --key <spec-<id>|quick-<runId>> --run <runId> --outcome <landed|chained|hold|stop|blocked>`: legge da stdin da 1 a 5 punti elenco di lezioni (righe `- ` di al massimo 300 caratteri ciascuna) e li aggiunge come sezione `## <runId> — <outcome> (<date>)` alla nota con topic key `emet/<repo>/lessons/<key>`, oppure crea quella nota. Una nota oltre i 20000 caratteri scarta le sezioni più vecchie. Stampa `{available: true, saved: true, topicKey}`.
  - Entrambi i sottocomandi parlano con Engram avviando `engram mcp --tools=agent` nella radice del repo; il plugin Engram non è richiesto. Non passano mai un `project` a Engram.
  - Codici di uscita: `2` per un uso errato (nessun sottocomando, query mancante, nessun punto elenco, più di 5 punti elenco, un punto elenco oltre 300 caratteri, un esito sconosciuto, una key non valida). Ogni problema di Engram (non nel PATH, handshake fallito, errore di uno strumento, timeout, JSON malformato) esce con `0`. Prima di un handshake riuscito l'output è `{available: false, reason}`; dopo, `{available: true, results: [], reason}` per `search` oppure `{available: true, saved: false, reason}` per `save`. `memory.enabled: "off"` stampa `{available: false, reason: "memory.enabled is off"}` e non avvia nulla. Vedi [`memory`](configuration.md#memory).
- `emet insights [--since <iso|7d|30d>] [--repo <path>] [--all] [--json] [--mark-baseline]`: legge il [diario degli eventi](../guide/journal.md) e riporta le esecuzioni per origine (umana o auto), le decisioni del gate per decisione e motivo, gli interventi umani per esecuzione, gli esiti dei lanci e i ticket chiusi. Le righe illeggibili vengono saltate e contate. `--mark-baseline` aggiunge una baseline; i report successivi coprono solo gli eventi dopo di essa, a meno di `--all`. Un diario vuoto o mancante stampa un report a zero ed esce con 0.
- `emet usage [--session <id> | --file <path>] [--stalled [--minutes N]] [--project-dir <path>]`: riporta l'uso della sessione; `--stalled` elenca i worker bloccati.
- `emet handoff --check <path> [--expect-skills a,b] | --render <path>`: valida o rende la nota `.emet/handoff-<ticket>.md` di un worker. La nota può contenere una sezione `skills:`, scritta `skills: none` oppure `skills: loaded: a, b; missing: c`; è richiesta solo quando `state` è `done`, e qualsiasi altro valore fa fallire il controllo. `--expect-skills a,b` (solo con check) fa fallire il controllo per ogni skill indicata che non compare né nell'elenco `loaded` né in quello `missing`. Un controllo superato stampa `missing skills: …` quando l'elenco `missing` non è vuoto.
- `emet metrics [--run <id>]`: riporta token, costo equivalente in API e tempo di esecuzione per ticket, per ondata e per esecuzione, letti dalle trascrizioni delle sessioni. Confronta inoltre il budget di contesto stimato per ticket con quello effettivamente usato da ogni worker. Il suo riepilogo va in fondo al report finale dell'esecuzione.

### Pianificazione, review e landing

- `emet promote --spec <id> [--dry-run] [--no-promote] [--hold]`: il passo after-spec, secondo [`handoff.afterSpec`](configuration.md#handoff). In modalità `promote` apre una pull request da `develop` a `main` con titolo `chore: 🔖 promote develop`, attende con `emet ci --pr <n> --wait`, la unisce con un merge commit solo quando lo stato è `pass`, poi, solo se `develop` è indietro rispetto a `main`, apre una pull request di sincronizzazione da `main` a `develop`, ne attende i check allo stesso modo e la unisce con un merge commit solo quando lo stato è `pass`; una pull request di sincronizzazione il cui stato è `fail`, `timeout` o `env-fault`, o il cui merge viene rifiutato, resta aperta e non cambia mai l'esito di promote. Aggiunge al journal un evento `promote` con il numero della pull request, `merged`, `syncPrNumber`, `syncMerged`, `syncReason`, `rule` e `reason`. `afterSpec` può essere un elenco di regole; la modalità viene allora scelta in base ai percorsi che la promozione di `develop` porterebbe (vedi [`handoff.afterSpec`](configuration.md#handoff)), e un `git fetch` o `git diff` che fallisce fa uscire il comando con 1 prima di aprire qualsiasi pull request. L'esito stampato contiene `rule` (l'indice della regola corrispondente, oppure `null` per la forma stringa o senza corrispondenza), `reason`, `syncPrNumber` (`null` quando non è stata aperta alcuna pull request di sincronizzazione), `syncMerged` e `syncReason` (una frase che spiega perché una pull request di sincronizzazione è rimasta aperta, altrimenti `null`) e `deployCheck: { run, reason }`, che indica se il coordinatore deve eseguire `emet deploy-check`. In modalità `release` non unisce nulla e lascia la pull request di release a una persona. Con `afterSpec` `none`, con `--no-promote`, o quando l'ultima wave della spec è stata lasciata aperta o segnalata, esce con 0 e una nota `skipped`; viene comunque eseguito dopo un'ultima wave pulita, così che l'esito contenga la decisione `deployCheck` (sul trunk `main` il controllo di deploy viene eseguito qualunque sia la modalità). Una CI diversa da `pass` non unisce nulla ed esce con 1. `--dry-run` non apre alcuna pull request. `emet promote --spec <id> --hold` scrive il marcatore `<run dir>/runs/<id>/no-promote` e stampa `{"held":true}`; finché esiste, `emet promote --spec <id>` esce con 0 e una nota `skipped` senza aprire alcuna pull request, così `--no-promote` persiste tra le sessioni di una specifica.
- `emet deploy-check [--json]`: esegue `deploy.check.command` finché esce con 0, fino a `retries` tentativi o `timeoutSeconds`, attendendo `intervalSeconds` tra l'uno e l'altro, e stampa `state: ok | failed | timeout` con `attempts`. Uscita `0` ok, `1` failed, `3` timeout. Senza `deploy.check` configurato esce con 0 e `skipped: "no deploy check configured"`. Il coordinatore lo esegue solo quando l'esito di `emet promote` ha `deployCheck.run` a true. Vedi [`deploy`](configuration.md#deploy).
- `emet validate --spec <id> | --file <path>`: validazione del piano; vedi [Gate e registri](#gate-e-registri).
- `emet surfaces --check <file.json | ->`: rifiuta glob di superfici consentite sovrapposti tra i ticket di un'ondata.
- `emet approve --run <id>`, `emet materialize-log`, `emet results`, `emet verify`, `emet review-package`, `emet review`, `emet gate`: vedi [Gate e registri](#gate-e-registri).
- `emet approve --run <id> --spec <file> [--tickets <file>] --quick`: scrive `"mode": "quick"` in `approval.json`. Senza `--quick` il campo è assente e i record scritti prima di questa modifica superano comunque `--check`. `emet landed`, `emet status` ed `emet preflight` leggono l'unità di landing tramite `resolveLandingUnit`, che restituisce `"wave"` per una **Quick run** e `landing.unit` altrimenti, quindi una Quick run non si aspetta mai un branch della spec.
- `emet assess --base <ref> --head <ref>`: classifica un diff come `passive`, `medium` o `high` e stampa un JSON con il livello, i motivi e il modello e l'impegno consigliati per il reviewer, più `browserVerify: { run, reason }`: `run` è `true` solo quando il livello ha un reviewer, [`verify.browser`](configuration.md#verify) è configurato, il binario `agent-browser` è nel PATH e, quando `paths` è impostato, un percorso modificato corrisponde; altrimenti `reason` indica la prima condizione non soddisfatta. Vedi [Modelli e impegno](../../README.md#models--effort) e [`review`](configuration.md#review). Con `--quick` stampa lo stesso JSON più `"quickRejected": true|false` ed esce con 1 quando il tier è `high`, con 0 altrimenti; senza `--quick` output e codici di uscita non cambiano. `/emet:run --quick` tratta l'uscita 1 come uno **Stop** del gate. Stampa anche `dualReview: { run, reason }`: `run` è `true` solo quando il livello è `high`, `agentHost` è `claude`, [`review.dual`](configuration.md#review) non è `off` e il binario `codex` è nel PATH; altrimenti `reason` indica la prima condizione non soddisfatta.
- `emet land --spec <s> --branch <integration> --tickets <id,...>`: unisce un branch di integrazione nel trunk locale (`landing.mode` `merge`). `commands.selfCheck` sostituisce la CI e non viene inviato nulla.
- `emet spec-branch ensure|integrate|status|sync|land|abandon --spec <id>`: il branch della spec `spec/<id>` di `landing.unit: spec` (vedi [`landing`](configuration.md#landing)). Tutti stampano JSON. `ensure` crea il branch dal trunk (idempotente), scrive `.emet/specs/<id>/branch.json` e rifiuta quando è in checkout il branch di un'altra spec. `integrate --wave <n> --branch <integration> --tickets a,b` unisce il branch dell'ondata in `spec/<id>` con `--no-ff` e i trailer `Emet-Wave` ed `Emet-Tickets`, registra l'ondata, aggiunge `spec.integrate` e, quando `landing.pushSpecBranch` è true, fa push del branch senza aprire una PR. `status` stampa `branch`, `tip`, le ondate e i ticket integrati e `behindTrunk`, e ricostruisce `branch.json` dai trailer quando manca un'ondata. `sync` unisce il trunk nel branch, non fa mai rebase e, in caso di conflitto, annulla, elenca i percorsi ed esce con codice diverso da zero. `land [--partial]` sincronizza, poi in modalità `pr` fa push del branch, apre una PR con una riga `Closes` per ticket, attende i suoi controlli e unisce con `landing.specMergeMethod` (un merge commit per impostazione predefinita, ignorando `pr.mergeMethod`), e in modalità `merge` unisce nel trunk locale con `--no-ff` e non fa mai push; aggiunge `spec.land`. `abandon --force` etichetta `abandoned/spec-<id>`, elimina il branch, aggiunge `spec.abandon` e riporta a `ready-for-agent` i ticket integrati di un tracker locale; senza `--force` rifiuta. `emet tracker frontier` conta i ticket elencati in `branch.json` come bloccanti chiusi, e `emet status` guadagna `specBranch` (`branch`, `tip`, `integratedWaves`).
- `emet spec-merge --spec <id>`: fonde i delta dei requisiti `ADDED`/`MODIFIED`/`REMOVED` della spec in `docs/specs/<area>.md` (`specs.dir`). Con `specs.enabled` attivo, il coordinatore scrive i delta e lo esegue una volta per spec, sul branch di integrazione dell'ultima ondata prima della sua review, poi fa il commit del risultato. `--deltas-dir` stampa la directory in cui vanno i delta. Controlla ogni area prima di scrivere qualcosa. Un conflitto, o un requisito che perderebbe uno scenario, esce con 1 e lascia ogni file intatto. Con `specs.enabled` disattivato non fonde nulla ed esce con 0.
- `emet map [--refresh]`: scrive una sintesi di un codebase esistente (stack, struttura, convenzioni, test, hotspot) in `docs/agents/codebase.md` (`map.path`), marcata con lo SHA del commit da cui è stata costruita. Lo stesso commit produce sempre lo stesso file. `emet map --stale` esce con 1 quando HEAD ha superato il marcatore, e in tal caso `emet preflight` avvisa. `emet map --for <globs>` stampa solo le sezioni che corrispondono alle superfici di modifica di un ticket; quell'output è l'unica parte della mappa inclusa nel brief di un worker.
- `emet tracker create-spec|create-ticket|read|frontier|set-state|comment|close`: il tracker locale su `.scratch/`, JSON su stdout. Vedi [Tracker locale](#tracker-locale).
- `emet guard`: l'hook `PreToolUse` di Claude Code; legge il JSON dell'hook da stdin (la forma Codex è sotto [Host Codex](#host-codex)). `install.sh` lo collega in `~/.claude/settings.json`. Blocca una manciata di inneschi noti di fallimenti nelle esecuzioni senza supervisione (vedi `emet/src/guard.ts`).

### Tracker locale

Con `tracker.kind: "local"`, spec e ticket sono file markdown sotto `.scratch/` del worktree principale (non versionato): `.scratch/<slug>/spec.md` e `.scratch/<slug>/issues/<NN>-<slug>.md`, ciascuno con righe `Status:` e `Blocked by:` e commenti sotto `## Comments`. Il coordinatore li legge e li scrive tramite `emet tracker` (`create-spec`, `create-ticket`, `read`, `frontier`, `set-state`, `comment`, `close`). `emet init --tracker local` lo configura. Vedi [ADR-0011](../adr/0011-local-tracker-scratch-convention.md).

`landing.mode` è `"pr"` (predefinito) o `"merge"`, indipendente dal tracker. In modalità `merge` un'ondata atterra come un unico merge locale nel trunk con `emet land`, con `commands.selfCheck` al posto della CI e senza push. Con `landing.unit: "spec"` (predefinito) l'intera spec atterra una volta con `emet spec-branch land`. `gh` serve solo quando il tracker è `github` o il landing è `pr`. Vedi [ADR-0010](../adr/0010-local-merge-landing.md) e [`landing`](configuration.md#landing).

### PR di landing e concatenamento delle ondate

Con `landing.unit: "wave"`, un'ondata è una PR; con `"spec"`, una PR copre tutte le ondate integrate. Il suo corpo contiene una riga `Closes #N` per ogni ticket (la parola chiave di chiusura del tracker), e il coordinatore sposta i ticket in in-review quando apre la PR. La PR viene poi unita secondo `pr.autoMerge`, oppure resta aperta quando l'ondata è stata segnalata, `autoMerge` è `false` o le correzioni di CI sono esaurite (la PR riceve allora l'etichetta human-decision). Le ondate successive girano in sessioni proprie, mai in quella che ha eseguito l'ondata 1. Le sezioni `pr` e `handoff` controllano cosa accade dopo; vedi [`pr`](configuration.md#pr) e [`handoff`](configuration.md#handoff).

`emet ci --pr <n> --wait [--rerun-flakes] [--timeout-minutes <m>]` interroga i check della PR finché non terminano o scade il timeout (predefinito 30). Con `--rerun-flakes` riesegue una volta ogni check fallito tramite `gh run rerun --failed`; un check che passa alla riesecuzione è un Flake. Stampa `state: pass | fail | env-fault | timeout`, i check falliti e `flakeReruns`, e non esegue mai il merge. Una PR senza check è `pass` con `noChecks: true`. Codice `0` pass, `1` fail o env-fault, `3` timeout. `env-fault` indica check terminati con `STARTUP_FAILURE` o rimasti in coda troppo a lungo: una CI mai eseguita, non un errore del codice.

Con `tracker.kind: "github"`, `emet tracker close <ticket>... [--pr <n>]` chiude ogni ticket (`CLA-<n>`, `#<n>` o un numero nudo) con `gh issue close --reason completed`, ne verifica lo stato e riporta `closed` o `already-closed`. `--pr` aggiunge il commento "Landed in #<n>". Poi, per ogni genitore distinto di un ticket `closed` o `already-closed`, legge `gh issue view <spec> --json state,subIssuesSummary`; se la spec è aperta e `subIssuesSummary.completed` è uguale a un `total` diverso da zero, chiude la spec con `gh issue close --reason completed` e il commento "All <total> tickets landed.", poi ne verifica lo stato. L'output guadagna `specs`, un `{ spec, outcome, detail? }` per ogni genitore distinto con esito `closed`, `open`, `already-closed` o `failed`; un ticket senza genitore non aggiunge nulla, e una lettura o chiusura di spec fallita non cambia mai l'esito di un ticket. Termina con `1` se un ticket o una spec è fallito, dopo aver elaborato gli altri. I ticket Linear sono confermati Done dal coordinatore tramite l'MCP di Linear.

### Host Codex

Questi comandi servono l'host di agente Codex (`agentHost` `"codex"`); vedi la [guida a Codex](../guide/codex.md).

- `emet dispatch --role worker --run <id> --ticket <id> --prompt-file <file> [--model <m>] [--effort <e>] [--root <dir>]`: dopo aver controllato la prenotazione e lo slot, crea `.emet/worktrees/agent-<ticket>`, costruisce un overlay `CODEX_HOME` per esecuzione e avvia il worker come `codex exec` distaccato. `emet dispatch --wait --run <id> --ticket <id> [--timeout <s>]` attende la fine e stampa lo stato di risultato registrato.
- `emet review-run --run <id> --ticket <id> --package <file> --tier <medium|high|passive> [--browser-verify true|false]`: esegue il reviewer come `codex exec` in sola lettura su un pacchetto di `emet review-package` e stampa il JSON dei rilievi per `emet review --findings`. Il livello `passive` non avvia alcun processo. `--browser-verify` ha come predefinito `false`; con `true` il prompt termina con l'asse Browser, con `--session review-<run>` compilato a partire da `--run`, così il reviewer Codex verifica la UI come fa il reviewer Claude (passalo quando `emet assess` ha stampato `browserVerify.run: true`; vedi [`verify`](configuration.md#verify)). Senza il flag il prompt non cambia, e un valore diverso da `true` o `false` termina con codice 2 e la riga di utilizzo. `--coverage-out <file>` scrive in un file i verdetti di copertura (Coverage verdicts) del reviewer Codex; si usa sull'host Codex, dove gira un solo reviewer, e lo stdout continua a stampare i rilievi. L'output dei rilievi accetta anche i campi facoltativi `s` e `userOption`.
- `emet launch <spec-id> --wave <n>`: su questo host, avvia un `codex exec` distaccato che esegue `$emet:run --dispatch <spec>` e registra il suo id di thread. Non si apre alcuna scheda Orca, e `codex exec resume <id>` riprende la sessione.
- `emet guard`: con `EMET_AGENT_HOST=codex` legge l'input degli hook di Codex, controlla i percorsi di `apply_patch` rispetto a `.emet/surface.json` e tiene chiuso il cancello di approvazione finché non arriva una riga di prompt `approve <id>`.

## Gate e registri

Le fasi non decidono da sole quando un ticket è finito, unibile o vale un altro tentativo. Chiamano un comando della CLI che legge un registro su disco e stampa la decisione. I registri di esecuzione stanno sotto `.emet/runs/<run-id>/` e il ledger delle review sotto `.emet/review/`, nel checkout principale, non nel worktree di un worker.

| Passo                   | Comando                                              | Cosa impone                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Prima dell'approvazione | `emet validate --file <plan.json>`                   | Ogni `S#` è coperto da almeno un ticket e ha uno scenario di accettazione. Ogni ticket copre almeno un `S#`. Le superfici di modifica sono disgiunte all'interno di un'ondata. Nessun ciclo di dipendenze. Con [`validate.coupledSurfaces`](configuration.md#validate), un errore `coupled-surface-split` quando un ticket che tocca il `source` di una coppia si trova in un'ondata precedente a quella di un ticket che tocca i suoi `dependents` (uscita 1). `emet preflight` lo esegue di nuovo sul piano approvato. Un piano senza ticket produce un errore `no-tickets` ("plan has no tickets; write one folded ticket"), con o senza elementi `S#` nella spec; un solo ticket con `folded: true` che copre ogni `S#` lo supera.                                                                                                           |                                                                                                                                                                                                                                                                                                                                                                                                                             | Approvazione | `emet approve --run <id> --spec <file>` | Scrive `approval.json` con gli hash della spec e dell'elenco dei ticket. Il dispatch rifiuta se uno dei due cambia dopo (`--check`). |
| Creazione dei ticket    | `emet materialize-log --run <id> --record/--lookup`  | Salva l'ID di ogni ticket creato non appena esiste, così un'esecuzione interrotta non crea mai duplicati.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Worker terminato        | `emet results --run <id> --write/--read <ticket>`    | I worker scrivono un file di risultato locale (`DONE`, `DONE_WITH_CONCERNS`, `BLOCKED` o `NEEDS_CONTEXT`, più una riga `Risk:`). Solo il coordinatore scrive sul tracker.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Dopo ogni worker        | `emet verify <ticket> --run <id>`                    | Verifica che esistano commit oltre la base del dispatch, che ogni percorso modificato sia dentro le superfici di modifica del ticket, che la nota di handoff superi `handoff --check` e che `commands.workerScopedSuite` passi. | Input della review      | `emet review-package <base> <head> --out <file>`     | Raggruppa il diff per il reviewer, che lo riceve come percorso di file. Esce con 3 se l'intervallo è vuoto o non discende da base.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Review                  | `emet review --ticket <t> --findings <file>`         | Tiene il ledger dei rilievi e impone l'ordine di triage (`intent_gap` → `bad_plan` → `patch` → `defer`) e il limite di round. `--recheck --verdicts <file>` chiude un round di correzione: vengono valutati solo i rilievi aperti al suo inizio, un rilievo diventa `resolved` solo tramite un verdetto, e il recheck conta contro `budgets.fixRounds` (codice 1 che indica il limite quando è esaurito). `--escalate` passa al livello di modello successivo. `--rule`/`--rulings` registrano ed elencano i "Rulings I made" per il report e il corpo della PR. `--base <ref>` al primo round risolve il riferimento in uno sha e lo salva nel ledger; i rilievi su righe che l'ondata non ha toccato vengono salvati con `preexisting: true` e `emet gate` non li conta mai come bloccanti, a meno che portino `userOption`. `--coverage <file | -> [--expect S1,S3]`salva i verdetti di copertura`{s, verdict, test:{file,name}}`e apre un rilievo`VG-S<n>`(verification-gap) per ogni`met`senza prova e per ogni S# atteso senza verdetto; non usa alcun round. ## Codici di uscita

I codici di uscita hanno lo stesso significato in ogni sottocomando.

| Codice | Significato                                                                                                  |
| ------ | ------------------------------------------------------------------------------------------------------------ |
| `0`    | Pulito.                                                                                                      |
| `1`    | Rilievi su cui agire.                                                                                        |
| `2`    | Errore di configurazione o di utilizzo; lo strumento non è mai stato eseguito. Anche un comando sconosciuto. |
| `3`    | Errore interno.                                                                                              |

Anche un flag sconosciuto termina con `2` e nomina il flag. Ctrl-C termina con `130`.

## Flag globali

Ogni comando li accetta; i flag propri di ciascun comando sono elencati da `emet <command> --help`.

| Flag         | Effetto                                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------------------------- |
| `--json`     | Stampa un'unica envelope `{ok, data, error: {code, message, fix}}` su stdout, anche per `--help` e `--version`.     |
| `--no-color` | Disattiva il colore ANSI. Il colore rispetta anche `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb` e se l'output è un TTY.   |
| `--verbose`  | Stampa lo stack di un errore imprevisto. Senza di esso, il catch di livello superiore stampa un errore di una riga. |
| `--help`     | Stampa l'uso del comando.                                                                                           |

`emet --version` stampa la versione; `emet --version --json` stampa `{"ok": true, "data": {"version": ...}, "error": null}`. Con `--json`, un comando che fallisce termina con il suo codice abituale e stampa `ok: false` con un `code` di errore tra `findings`, `usage`, `internal`, `slice-timeout`, `expired`, `bad-range` o `exit-<n>`; ciò che il comando ha stampato su stdout è il `data` dell'envelope.

Su un TTY, `emet` stampa un avviso di una riga su stderr quando è nota una release più recente. Controlla al massimo una volta al giorno, mette in cache la risposta, non attende mai la rete e resta silenzioso con `--json` o senza TTY.

## Variabili d'ambiente

Variabili rivolte all'utente. Una variabile, se impostata, sostituisce il valore di configurazione corrispondente.

| Variabile                     | Effetto                                                                                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `EMET_SKIP_DEPENDENCY_CHECKS` | `EMET_SKIP_DEPENDENCY_CHECKS=1 emet preflight` declassa un blocco per dipendenze a un avviso per quella sola esecuzione. Impostala nella tua shell, non in qualcosa che il coordinatore esegue senza supervisione. |
| `EMET_MAX_LIVE_WORKERS`       | Sostituisce [`concurrency.maxLiveWorkers`](configuration.md#concurrency); accetta un intero positivo o `auto`.                                                                                                     |
| `EMET_RUN_IDLE_THRESHOLD_MS`  | Sostituisce [`concurrency.runIdleThresholdMs`](configuration.md#concurrency), in millisecondi.                                                                                                                     |
| `EMET_STATE_DIR`              | Directory di stato dell'host, che contiene il pool di slot dei worker. Ordine di risoluzione: `$EMET_STATE_DIR`, poi `$XDG_STATE_HOME/emet`, poi `~/.local/state/emet`.                                            |
| `EMET_MEM_RESERVE_GIB`        | Margine di memoria in GiB che deve restare libero; un acquire viene negato quando la memoria disponibile è inferiore. Predefinito 8. Alimenta anche il limite `auto` dei worker.                                   |
| `EMET_MEM_PER_WORKER_GIB`     | Memoria in GiB ipotizzata per worker quando `maxLiveWorkers` è `auto`. Predefinito 2. Aumentalo per uno stack per worker più pesante, come una suite E2E guidata da browser per ogni worktree.                     |
| `EMET_CPU_OVERSUBSCRIBE`      | Moltiplicatore di CPU per il limite `auto` dei worker. Predefinito 1.                                                                                                                                              |
| `EMET_AGENT_HOST`             | `codex` fa leggere a `emet guard` l'input degli hook di Codex. Impostata dagli hook di Codex; lasciala non impostata su Claude Code.                                                                               |

Il limite `auto` è `clamp(min(cpuCount × EMET_CPU_OVERSUBSCRIBE, floor((memTotal − EMET_MEM_RESERVE_GIB) / EMET_MEM_PER_WORKER_GIB)), min, max)`. I vecchi nomi `FORGE_*` sono ancora letti; `EMET_*` ha la precedenza quando entrambi sono impostati.
