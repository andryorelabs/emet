Jeder `emet`-Unterbefehl, die Tabelle der Gates und Aufzeichnungen, Exit-Codes und Umgebungsvariablen. Die Begriffe folgen [GLOSSARY.md](../../GLOSSARY.md). Zurück zur [README](../../README.md). Jeder Befehl gibt seine Verwendung mit `--help` aus.

## Unterbefehle

Drei Slash-Befehle umhüllen die CLI innerhalb von Claude Code: `/emet:run` (die Pipeline), `/emet:init` (`emet init`) und `/emet:doctor` (`emet doctor .`). Unter Codex sind es die Skills `$emet:run`, `$emet:init` und `$emet:doctor`. Ein `emet` in einem normalen Terminal benötigt `install.sh`; andernfalls `! emet <subcommand>` innerhalb einer Sitzung ausführen.

`emet <command> [...args]`. `emet --version` gibt die Version aus.

### Einrichtung und Prüfung

- `emet migrate [--dry-run]`: benennt ein Legacy-Repo auf die emet-Namen um.
- `emet init [--tracker linear|github|local] [--after-spec release|promote|none] [--force]`: erkennt Paketmanager, Trunk-Branch, Tracker-Art und After-Spec-Modus automatisch (siehe [`handoff.afterSpec`](configuration.md#handoff)), setzt [`schema.ownedPaths`](configuration.md#schema), wenn es ein Prisma-Schema (`prisma/schema.prisma` oder einen Ordner `prisma/schema/`) oder einen Drizzle-Migrationsordner (`drizzle/` neben einer `drizzle.config.*`) findet, und schreibt `emet.config.json` und die `docs/agents/*.md`-Dateien. `--tracker local` richtet den lokalen Tracker ein.
- `emet doctor [--all] [<path> ...]`: schreibgeschützte Prüfung beliebig vieler Repos gleichzeitig; Standard ist das aktuelle Verzeichnis. Für ein Repo, das [`verify.browser`](configuration.md#verify) konfiguriert, meldet es außerdem einen optionalen `agent-browser`-Befund: Eine fehlende Binärdatei ist `indeterminate` (eine `optional:`-Zeile mit einem Installationshinweis), und wenn die Binärdatei existiert, erscheint ein fehlschlagendes `agent-browser doctor` als Warnung. Keines von beidem ist je ein Fehler, und keines ändert den Exit-Code. Ein Repo ohne `verify.browser` zeigt nichts an.
- `emet setup [--yes] [--with <ids>] [--list] [--json]`: bietet die optionalen Installationen über readline-Abfragen an: `mattpocock-skills` (standardmäßig an), `engram`, `mascot`, `orca-pet`, `gh-auth`, `agent-browser` (standardmäßig aus; führt `bun add -g agent-browser@latest` und dann `agent-browser install` aus, schreibt `~/.agent-browser/config.json` mit `contentBoundaries: true` und `maxOutput: 50000` nur, wenn diese Datei nicht existiert, führt dann `agent-browser doctor` aus und gibt eine Warnung aus, wenn der Befehl fehlschlägt; pinnt nie eine Version und übergibt nie `--with-deps`, sodass es bei fehlenden Systembibliotheken den Befehl ausgibt, den Sie selbst ausführen), `context7` (standardmäßig aus; führt `bun add -g ctx7@latest` aus, dann immer `ctx7 setup --cli --claude --yes` und zusätzlich, nur wenn `codex` im PATH liegt, `ctx7 setup --cli --codex --yes`; installiert die `ctx7`-CLI und ihren `find-docs`-Skill, nicht den MCP-Server, pinnt nie eine Version und gibt den Befehl zum manuellen Ausführen aus, wenn ein `ctx7 setup`-Schritt fehlschlägt; `ctx7` sendet anonyme Nutzungsereignisse, sofern `CTX7_TELEMETRY_DISABLED=1` nicht gesetzt ist, und ein `CONTEXT7_API_KEY` in der Umgebung hat Vorrang vor dem mit `ctx7 login` gespeicherten Konto), `firecrawl-local` (standardmäßig aus; benötigt `cargo`, führt `cargo install firecrawl-local` aus, wenn die Binärdatei fehlt, und registriert dann einen Claude-Code-MCP-Server im Benutzerbereich mit `FIRECRAWL_CLOUD=search` und `--public-only` und ersetzt dabei eine frühere Registrierung mit anderen Einstellungen: Scrape, Crawl und Map laufen auf dem Rechner, nur die Websuche geht an Firecrawl Cloud, und private Adressen werden blockiert. Es übergibt das neueste von `agent-browser` heruntergeladene Chrome als `FIRECRAWL_CHROME_PATH`; unter Linux, wo AppArmor unprivilegierte User-Namespaces einschränkt, gibt es ein AppArmor-Profil und die `sudo`-Befehle zum Laden aus, weil Firecrawl Local Chrome nie ohne seine Sandbox startet. Ohne nutzbares Chrome bleiben Seiten, die mit JavaScript rendern, leer) und die empfohlenen Claude-Code-Einstellungen (`claude-settings`, nur bei Auswahl angewendet, nach einem Backup von `settings.json` mit Zeitstempel). Ohne TTY oder mit `--yes` oder `--with` fragt es nichts und installiert genau die genannten Einträge; ohne TTY und ohne `--with` installiert es nichts und gibt den `--list`-Katalog aus. Jeder Schritt meldet `installed`, `already-present`, `skipped` oder `failed`; ein Fehler stoppt die anderen nicht, und der Exit-Code ist 1, wenn etwas fehlgeschlagen ist. `/emet:setup` ist der Plugin-Einstieg und stellt dieselben Fragen mit `AskUserQuestion`.
- `emet fleet list [--root <dir>] [--json]`: listet die Git-Repos mit einer `emet.config.json` eine Ebene unter `--root` (Standard `~/code`) auf, mit `tracker.kind`, `handoff.autoChain` und `models.worker`. `emet fleet set <key> <value> [--root <dir>] [--dry-run]` ändert einen Konfigurationsschlüssel in jedem aufgelisteten Repo und validiert vorher über den Config-Loader (ein ungültiger Wert ändert nichts und beendet mit 1). `emet fleet launch --feature <text> [--root <dir>] [--repos <a,b>]` öffnet in jedem Repo eine `/emet:run --draft <text>`-Sitzung nach den Bereitschaftsprüfungen von `emet chain`. Siehe den [Fleet-Leitfaden](../guide/fleet.md).
- `emet preflight [--run <id>] [--post-dispatch]`: bestätigt, dass das Repo bereit für den Dispatch ist.
- `emet skill-path <name>`: gibt den absoluten `SKILL.md`-Pfad eines mattpocock-skills-Skills aus. Endet mit Exit-Code 1, wenn der Skill nicht gefunden wird.
- `emet selftest`: führt die eigenen Unit-Tests der CLI aus. Nur bei Quellcode-Installationen; eine kompilierte Binärdatei endet mit Exit-Code 1 und verweist auf `emet doctor`.

In einem beliebigen Git-Repo:

```bash
emet init          # autodetects package manager, trunk branch, tracker kind
emet preflight      # confirms the repo is dispatch-ready
```

`emet init` hinterlässt in den erzeugten `docs/agents/*.md`-Dateien eine `TODO(emet):`-Markierung für alles, was es nicht selbst ableiten kann (eine gemeinsame Testdatenbank-Sperre, Schema-Zuständigkeit und so weiter). Diese ausfüllen; `emet preflight` verweigert den Dispatch, solange eine übrig ist.

Danach, in Claude Code (unter Codex `$emet:run` mit denselben Argumenten verwenden):

```text
/emet:run <describe the feature>              # interview → wave 1; later waves via --dispatch/autoChain
/emet:run --draft <describe the feature>      # stop after tickets are created
/emet:run --dispatch <spec-id>                # dispatch a --draft'd spec later
```

#### Flottenprüfung

`emet doctor` prüft mehrere Repos gleichzeitig und nur lesend:

```bash
emet doctor ~/code/*
```

Der Bericht enthält pro Repo: eine gültige `emet.config.json`, alle vier vorhandenen `docs/agents/*.md`-Dateien, keine übrig gebliebenen `TODO(emet):`-Markierungen, ob die Befehle in `commands.selfCheck` tatsächlich aufgelöst werden, sowie die trackerspezifischen Abhängigkeitsbefunde des Repos (`gh`, Linear; siehe [Abhängigkeiten](dependencies.md#was-was-prüft)). Das Plugin mattpocock-skills und die Flags der externen CLIs (`gh`, dazu die des Agent-Hosts: `claude --bg` und `claude agents --json` unter Claude Code, `codex exec --json` und `--output-schema` unter Codex, geprüft über `--help`) werden einmal für den gesamten Durchlauf geprüft, nicht pro Repo.

### Läufe, Worker und Slots

- `emet claims --reserve <ticket> --run <id> --anchor <pid>`: reserviert ein Ticket für einen Lauf. `--release <ticket>`, `--list` und `--prune [--dry-run]` geben einen Claim frei, listen Claims auf oder entfernen veraltete.
- `emet slots --acquire --run <id> --anchor <pid> --ticket <ticket>`: nimmt einen Worker-Slot aus dem hostweiten Pool in `~/.local/state/emet/slots`. `--release --run <id>`, `--release-index <index>` und `--list` geben Slots frei oder listen sie auf.
- `emet cleanup [--run <id> | --all] [--dry-run] [--force]`: ohne Argumente werden abgeschlossene oder tote Läufe zurückgewonnen, deren Arbeit gelandet ist; `--run` räumt diesen Lauf auf; `--all` ist ein repoweiter Branch-Durchlauf. Nach einem Merge gibt `emet cleanup --run <runId>` die Branches, Ticket-Claims und Worker-Slots der Welle frei. In jedem Modus löscht es außerdem jeden lokalen Branch, dessen PR am Tip-Commit des Branches gemergt wurde, zusammen mit dem sauberen, nicht gesperrten Agent-Worktree, der ihn enthält.
- `emet lock-reason --run <id> --ticket <ticket> [--anchor <pid>]`: gibt den `git worktree lock`-Grund aus, den ein Worker beim Bootstrap schreibt.
- `emet launch <spec-id> --wave <n>`: startet unter Claude Code eine Welle als `claude --bg`-Sitzung und öffnet ihren Orca-Tab gemäß `handoff.launcher` (unter Codex siehe [Codex-Host](#codex-host)). Es erledigt den gesamten Start (Prüfung auf doppelte Sitzungen, `claude --bg`, Tab) und gibt `{ name, id, attach, orcaTab: { opened, reason } }` aus. Dieses statt eines bloßen `claude --bg` verwenden, wenn eine Welle von Hand in einer anderen Sitzung laufen soll.
- `emet chain --ticket <id> --spec <id> --wave <n> [gate flags]`: führt `emet gate` mit den übergebenen Gate-Flags aus und startet die nächste Welle nur, wenn die Entscheidung `chain` lautet. Vor dem Start prüft es die Bereitschaft (Speicherreserve des Hosts, freier Speicherplatz und Inodes im Repo und in `/tmp`, die `orca`-CLI) und bestätigt danach, dass die Kindsitzung aufgelistet ist. Jede andere Entscheidung, ein blockierendes Bereitschaftsproblem (`low-memory`, `low-disk`, `low-inodes`, `orca-unavailable`) oder eine bestehende Sitzung für dieselbe Spezifikation und Welle beendet mit Exit 1 samt Gründen und startet nichts.
- `emet status [--spec <id>] [--brief]`: Working / Checking / Ready / Needs-decision pro Welle als JSON plus eine Zusammenfassungszeile. `--brief` gibt stattdessen höchstens drei Zeilen aus: den Gesamtzustand, was auf eine Person wartet (falls etwas wartet) und die nächste Aktion. `emet status --help` dokumentiert das JSON.
- `emet run current [--json]`: gibt den aktiven Lauf des Repos aus (Lauf-ID, Spec, Welle, Phase und letzte Aktualisierung), gelesen aus `.emet/phase.json`. Ohne aktiven Lauf gibt es `no active run` aus und endet mit 0.
- `emet insights [--since <iso|7d|30d>] [--repo <path>] [--all] [--json] [--mark-baseline]`: liest das [Ereignisjournal](../guide/journal.md) und berichtet Läufe nach Ursprung (menschlich oder automatisch), Gate-Entscheidungen nach Entscheidung und Grund, menschliche Eingriffe pro Lauf, Start-Ergebnisse und geschlossene Tickets. Unlesbare Zeilen werden übersprungen und gezählt. `--mark-baseline` hängt eine Baseline an; spätere Berichte decken nur Ereignisse danach ab, außer `--all` ist angegeben. Ein leeres oder fehlendes Journal gibt einen Nullbericht aus und endet mit 0.
- `emet usage [--session <id> | --file <path>] [--stalled [--minutes N]] [--project-dir <path>]`: berichtet die Sitzungsnutzung; `--stalled` listet festgefahrene Worker auf.
- `emet handoff --check <path> | --render <path>`: validiert oder rendert die Notiz `.emet/handoff-<ticket>.md` eines Workers.
- `emet metrics [--run <id>]`: berichtet Tokens, API-äquivalente Kosten und Laufzeit pro Ticket, pro Welle und pro Lauf, gelesen aus den Sitzungsprotokollen. Es vergleicht außerdem das pro Ticket geschätzte Kontextbudget mit dem, was jeder Worker tatsächlich verbraucht hat. Die Zusammenfassung steht am Ende des Abschlussberichts des Laufs.

### Planung, Review und Landing

- `emet promote --spec <id> [--dry-run] [--no-promote] [--hold]`: der After-Spec-Schritt gemäß [`handoff.afterSpec`](configuration.md#handoff). Im Modus `promote` öffnet er einen Pull Request von `develop` nach `main` mit dem Titel `chore: 🔖 promote develop`, wartet mit `emet ci --pr <n> --wait`, mergt ihn mit einem Merge-Commit nur, wenn der Zustand `pass` ist, und öffnet und mergt dann einen Sync-Pull-Request von `main` nach `develop`, nur wenn `develop` hinter `main` liegt. Er hängt ein `promote`-Ereignis mit der Pull-Request-Nummer, `merged`, `rule` und `reason` an das Journal an. `afterSpec` kann eine Regelliste sein; der Modus wird dann aus den Pfaden gewählt, die ein Promoten von `develop` mitbringen würde (siehe [`handoff.afterSpec`](configuration.md#handoff)), und ein fehlschlagendes `git fetch` oder `git diff` lässt den Befehl mit 1 enden, bevor ein Pull Request geöffnet wird. Das ausgegebene Ergebnis enthält `rule` (den Index der passenden Regel oder `null` bei der String-Form oder ohne Treffer), `reason` und `deployCheck: { run, reason }`, das angibt, ob der Koordinator `emet deploy-check` ausführen soll. Im Modus `release` mergt er nichts und überlässt den Release-Pull-Request einer Person. Bei `afterSpec` `none`, mit `--no-promote` oder wenn die letzte Welle der Spec offen gelassen oder markiert wurde, beendet er mit 0 und einem `skipped`-Hinweis; er läuft dennoch nach einer sauberen letzten Welle, damit das Ergebnis die `deployCheck`-Entscheidung enthält (auf dem Trunk `main` läuft der Deploy-Check unabhängig vom Modus). Ein CI-Ergebnis ungleich `pass` mergt nichts und beendet mit 1. `--dry-run` öffnet keinen Pull Request. `emet promote --spec <id> --hold` schreibt die Markierung `<run dir>/runs/<id>/no-promote` und gibt `{"held":true}` aus; solange sie existiert, beendet sich `emet promote --spec <id>` mit 0 und einem `skipped`-Hinweis, ohne einen Pull Request zu öffnen, sodass `--no-promote` über die Sitzungen einer Spezifikation hinweg gilt.
- `emet deploy-check [--json]`: führt `deploy.check.command` aus, bis es mit 0 endet, höchstens `retries` Versuche oder `timeoutSeconds` lang, mit `intervalSeconds` Wartezeit dazwischen, und gibt `state: ok | failed | timeout` mit `attempts` aus. Exit `0` ok, `1` failed, `3` timeout. Ohne konfiguriertes `deploy.check` endet es mit 0 und `skipped: "no deploy check configured"`. Der Koordinator führt es nur aus, wenn das Ergebnis von `emet promote` `deployCheck.run` auf true hat. Siehe [`deploy`](configuration.md#deploy).
- `emet validate --spec <id> | --file <path>`: Planvalidierung; siehe [Gates und Aufzeichnungen](#gates-und-aufzeichnungen).
- `emet surfaces --check <file.json | ->`: weist überlappende Globs erlaubter Flächen zwischen den Tickets einer Welle zurück.
- `emet approve --run <id>`, `emet materialize-log`, `emet results`, `emet verify`, `emet review-package`, `emet review`, `emet gate`: siehe [Gates und Aufzeichnungen](#gates-und-aufzeichnungen).
- `emet assess --base <ref> --head <ref>`: klassifiziert einen Diff als `passive`, `medium` oder `high` und gibt JSON mit der Stufe, den Gründen und dem empfohlenen Reviewer-Modell samt Aufwand aus, dazu `browserVerify: { run, reason }`: `run` ist nur dann `true`, wenn die Stufe einen Reviewer hat, [`verify.browser`](configuration.md#verify) konfiguriert ist, die Binärdatei `agent-browser` im PATH liegt und, falls `paths` gesetzt ist, ein geänderter Pfad passt; andernfalls nennt `reason` die erste nicht erfüllte Bedingung. Siehe [Modelle und Aufwand](../../README.md#models--effort) und [`review`](configuration.md#review).
- `emet land --spec <s> --branch <integration> --tickets <id,...>`: mergt einen Integrationsbranch in den lokalen Trunk (`landing.mode` `merge`). `commands.selfCheck` ersetzt die CI, und es wird nichts gepusht.
- `emet spec-merge --spec <id>`: führt nach dem automatischen Merge einer Welle die Anforderungs-Deltas `ADDED`/`MODIFIED`/`REMOVED` der Spec in `docs/specs/<area>.md` (`specs.dir`) zusammen. Es prüft jeden Bereich, bevor es etwas schreibt. Ein Konflikt oder eine Anforderung, die ein Szenario verlieren würde, endet mit Exit-Code 1 und lässt jede Datei unberührt.
- `emet map [--refresh]`: schreibt eine Kurzbeschreibung einer bestehenden Codebase (Stack, Struktur, Konventionen, Tests, Hotspots) nach `docs/agents/codebase.md` (`map.path`), versehen mit dem Commit-SHA, aus dem sie erstellt wurde. Derselbe Commit erzeugt immer dieselbe Datei. `emet map --stale` endet mit Exit-Code 1, sobald HEAD über den Stempel hinausgewandert ist, und `emet preflight` warnt in diesem Fall. `emet map --for <globs>` gibt nur die Abschnitte aus, die zu den Bearbeitungsflächen eines Tickets passen; diese Ausgabe ist der einzige Teil der Karte, den ein Worker-Briefing enthält.
- `emet tracker create-spec|create-ticket|read|frontier|set-state|comment|close`: der lokale Tracker über `.scratch/`, JSON auf stdout. Siehe [Lokaler Tracker](#lokaler-tracker).
- `emet guard`: der `PreToolUse`-Hook von Claude Code; liest Hook-JSON von stdin (die Codex-Form steht unter [Codex-Host](#codex-host)). `install.sh` bindet ihn in `~/.claude/settings.json` ein. Er blockiert einige bekannte Auslöser für Fehler bei unbeaufsichtigten Läufen (siehe `emet/src/guard.ts`).

### Lokaler Tracker

Mit `tracker.kind: "local"` sind Specs und Tickets Markdown-Dateien unter `.scratch/` des Haupt-Worktrees (nicht versioniert): `.scratch/<slug>/spec.md` und `.scratch/<slug>/issues/<NN>-<slug>.md`, jeweils mit den Zeilen `Status:` und `Blocked by:` und Kommentaren unter `## Comments`. Der Koordinator liest und schreibt sie über `emet tracker` (`create-spec`, `create-ticket`, `read`, `frontier`, `set-state`, `comment`, `close`). `emet init --tracker local` richtet das ein. Siehe [ADR-0011](../adr/0011-local-tracker-scratch-convention.md).

`landing.mode` ist `"pr"` (Standard) oder `"merge"`, unabhängig vom Tracker. Im Modus `merge` landet eine Welle mit `emet land` als ein lokaler Merge in den Trunk, wobei `commands.selfCheck` die CI ersetzt und nichts gepusht wird. `gh` ist nur erforderlich, wenn der Tracker `github` ist oder das Landing `pr` verwendet. Siehe [ADR-0010](../adr/0010-local-merge-landing.md) und [`landing`](configuration.md#landing).

### Landing-PRs und Verkettung von Wellen

Eine Welle ist ein PR. Sein Text enthält für jedes Ticket eine Zeile `Closes #N` (das Schließ-Schlüsselwort des Trackers), und der Koordinator setzt die Tickets auf in-review, sobald er den PR öffnet. Der PR wird dann gemäß `pr.autoMerge` gemergt oder bleibt offen, wenn die Welle markiert wurde, `autoMerge` den Wert `false` hat oder die CI-Korrekturen aufgebraucht sind (der PR erhält dann das Label human-decision). Spätere Wellen laufen in eigenen Sitzungen, nie in der, die Welle 1 ausgeführt hat. Die Abschnitte `pr` und `handoff` steuern, was als Nächstes geschieht; siehe [`pr`](configuration.md#pr) und [`handoff`](configuration.md#handoff).

`emet ci --pr <n> --wait [--rerun-flakes] [--timeout-minutes <m>]` fragt die Checks des PRs ab, bis sie fertig sind oder das Timeout (Standard 30) abläuft. Mit `--rerun-flakes` wird jeder fehlgeschlagene Check einmal über `gh run rerun --failed` wiederholt; ein Check, der beim Wiederholen besteht, ist ein Flake. Es gibt `state: pass | fail | env-fault | timeout`, die fehlgeschlagenen Checks und `flakeReruns` aus und mergt nie. Ein PR ohne Checks ist `pass` mit `noChecks: true`. Exit `0` pass, `1` fail oder env-fault, `3` timeout. `env-fault` bedeutet Checks, die mit `STARTUP_FAILURE` endeten oder zu lange in der Warteschlange blieben: eine CI, die nie lief, kein Codefehler.

Bei `tracker.kind: "github"` schließt `emet tracker close <ticket>... [--pr <n>]` jedes Ticket (`CLA-<n>`, `#<n>` oder eine bloße Zahl) mit `gh issue close --reason completed`, prüft dessen Status und meldet `closed` oder `already-closed`. `--pr` fügt den Kommentar "Landed in #<n>" hinzu. Für jedes verschiedene Parent eines Tickets mit `closed` oder `already-closed` liest es danach `gh issue view <spec> --json state,subIssuesSummary`; ist die Spec offen und `subIssuesSummary.completed` gleich einem `total` ungleich null, schließt es die Spec mit `gh issue close --reason completed` und dem Kommentar "All <total> tickets landed." und prüft anschließend den Status. Die Ausgabe erhält `specs`, je ein `{ spec, outcome, detail? }` pro verschiedenem Parent mit dem Ergebnis `closed`, `open`, `already-closed` oder `failed`; ein Ticket ohne Parent fügt keinen Eintrag hinzu, und eine fehlgeschlagene Spec-Abfrage oder -Schließung ändert nie ein Ticket-Ergebnis. Es endet mit `1`, wenn ein Ticket oder eine Spec fehlgeschlagen ist, nachdem es die übrigen verarbeitet hat. Linear-Tickets bestätigt der Koordinator über den Linear-MCP als Done.

### Codex-Host

Diese Befehle bedienen den Codex-Agent-Host (`agentHost` `"codex"`); siehe den [Codex-Leitfaden](../guide/codex.md).

- `emet dispatch --role worker --run <id> --ticket <id> --prompt-file <file> [--model <m>] [--effort <e>] [--root <dir>]`: legt nach der Prüfung von Reservierung und Slot `.emet/worktrees/agent-<ticket>` an, baut ein `CODEX_HOME`-Overlay pro Lauf und startet den Worker als abgekoppeltes `codex exec`. `emet dispatch --wait --run <id> --ticket <id> [--timeout <s>]` blockiert bis zum Ende und gibt den aufgezeichneten Ergebnisstatus aus.
- `emet review-run --run <id> --ticket <id> --package <file> --tier <medium|high|passive> [--browser-verify true|false]`: führt den Reviewer als schreibgeschütztes `codex exec` über ein Paket von `emet review-package` aus und gibt Befunde-JSON für `emet review --findings` aus. Die Stufe `passive` startet keinen Prozess. `--browser-verify` ist standardmäßig `false`; mit `true` endet der Prompt mit der Browser-Achse, wobei `--session review-<run>` aus `--run` gefüllt wird, sodass der Codex-Reviewer die UI wie der Claude-Reviewer verifiziert (übergib es, wenn `emet assess` `browserVerify.run: true` ausgegeben hat; siehe [`verify`](configuration.md#verify)). Ohne das Flag bleibt der Prompt unverändert, und ein anderer Wert als `true` oder `false` beendet mit Exit 2 und der Usage-Zeile.
- `emet launch <spec-id> --wave <n>`: startet auf diesem Host ein abgekoppeltes `codex exec`, das `$emet:run --dispatch <spec>` ausführt, und speichert dessen Thread-ID. Es wird kein Orca-Tab geöffnet, und `codex exec resume <id>` setzt die Sitzung fort.
- `emet guard`: liest mit `EMET_AGENT_HOST=codex` die Hook-Eingabe von Codex, prüft die Pfade von `apply_patch` gegen `.emet/surface.json` und hält das Freigabe-Tor geschlossen, bis eine Prompt-Zeile `approve <id>` kommt.

## Gates und Aufzeichnungen

Die Phasen entscheiden nicht selbst, wann ein Ticket fertig, mergebar oder einen weiteren Versuch wert ist. Sie rufen einen CLI-Befehl auf, der eine Aufzeichnung auf der Festplatte liest und die Entscheidung ausgibt. Lauf-Aufzeichnungen liegen unter `.emet/runs/<run-id>/` und das Review-Ledger unter `.emet/review/`, im Haupt-Checkout, nicht im Worktree eines Workers.

| Schritt           | Befehl                                               | Was durchgesetzt wird                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Vor der Freigabe  | `emet validate --file <plan.json>`                   | Jedes `S#` wird von mindestens einem Ticket abgedeckt und hat ein Abnahmeszenario. Jedes Ticket deckt mindestens ein `S#` ab. Bearbeitungsflächen sind innerhalb einer Welle disjunkt. Keine Abhängigkeitszyklen. Mit [`validate.coupledSurfaces`](configuration.md#validate) ein `coupled-surface-split`-Fehler, wenn ein Ticket, das die `source` eines Paars berührt, in einer früheren Welle liegt als ein Ticket, das dessen `dependents` berührt (Exit 1). `emet preflight` führt es auf dem freigegebenen Plan erneut aus.                            |
| Freigabe          | `emet approve --run <id> --spec <file>`              | Schreibt `approval.json` mit den Hashes von Spec und Ticketliste. Der Dispatch wird verweigert, wenn sich eines davon danach ändert (`--check`).                                                                                                                                                                                                                                                                                                                                                                                                             |
| Ticket-Erstellung | `emet materialize-log --run <id> --record/--lookup`  | Speichert die ID jedes erstellten Tickets, sobald es existiert, sodass ein unterbrochener Lauf nie Duplikate erzeugt.                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Worker fertig     | `emet results --run <id> --write/--read <ticket>`    | Worker schreiben eine lokale Ergebnisdatei (`DONE`, `DONE_WITH_CONCERNS`, `BLOCKED` oder `NEEDS_CONTEXT`, plus eine `Risk:`-Zeile). Nur der Koordinator schreibt in den Tracker.                                                                                                                                                                                                                                                                                                                                                                             |
| Nach jedem Worker | `emet verify <ticket> --run <id>`                    | Prüft, dass Commits über die Dispatch-Basis hinaus existieren, jeder geänderte Pfad innerhalb der Bearbeitungsflächen des Tickets liegt, die Handoff-Notiz `handoff --check` besteht und `commands.workerScopedSuite` besteht. Review und Merge verweigern ein Ticket ohne Bestanden-Eintrag.                                                                                                                                                                                                                                                                |
| Review-Eingabe    | `emet review-package <base> <head> --out <file>`     | Bündelt den Diff für den Reviewer, der ihn als Dateipfad erhält. Endet mit Exit-Code 3, wenn der Bereich leer oder kein Nachfahre von base ist.                                                                                                                                                                                                                                                                                                                                                                                                              |
| Review            | `emet review --ticket <t> --findings <file>`         | Führt das Befund-Ledger und erzwingt die Triage-Reihenfolge (`intent_gap` → `bad_plan` → `patch` → `defer`) und die Rundengrenze. `--recheck --verdicts <file>` beendet eine Fix-Runde: Nur Befunde, die zu Beginn offen waren, werden bewertet, ein Befund wird nur durch ein Urteil `resolved`, und der Recheck zählt gegen `budgets.fixRounds` (Exit 1 mit Nennung der Grenze, wenn sie aufgebraucht ist). `--escalate` wechselt zur nächsten Modellstufe. `--rule`/`--rulings` erfassen und listen die „Rulings I made“ für den Bericht und den PR-Text. |
| Merge oder Kette  | `emet gate <ticket> --tier … --ci … --integration …` | Gibt `merge`, `hold`, `chain`, `stop` oder `defer` als JSON samt Begründungen aus. Es liest den Verify-Eintrag, die offenen Befunde, die Risikostufe, die CI, die Integrations-Suite und die Budgets. Ein `hold` trägt `next`: `fix-findings`, `rerun-failed-specs`, `rerun-ci` oder `report-infrastructure`. `--no-record` hält die Entscheidung aus dem Journal heraus. Siehe [`gate`](configuration.md#gate).                                                                                                                                             |

Nachdem die Branches einer Welle zusammengeführt wurden, läuft `commands.fullSuite` einmal auf dem Integrationsbranch. Ein roter Lauf blockiert den PR und `autoChain`. Das Gate erhält das Ergebnis als `--integration`. Zu den Budgets, die das Gate liest, siehe [`budgets`](configuration.md#budgets).

## Exit-Codes

Exit-Codes sind bei jedem Unterbefehl aussagekräftig.

| Code | Bedeutung                                                                                                   |
| ---- | ----------------------------------------------------------------------------------------------------------- |
| `0`  | Sauber.                                                                                                     |
| `1`  | Befunde, auf die reagiert werden muss.                                                                      |
| `2`  | Konfigurations- oder Verwendungsfehler; das Tool ist nie tatsächlich gelaufen. Auch ein unbekannter Befehl. |
| `3`  | Interner Fehler.                                                                                            |

Ein unbekanntes Flag beendet ebenfalls mit `2` und nennt das Flag. Strg-C beendet mit `130`.

## Globale Flags

Jeder Befehl akzeptiert diese; die eigenen Flags jedes Befehls listet `emet <command> --help` auf.

| Flag         | Wirkung                                                                                                                           |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `--json`     | Gibt ein Envelope `{ok, data, error: {code, message, fix}}` auf stdout aus, auch für `--help` und `--version`.                    |
| `--no-color` | Deaktiviert ANSI-Farben. Die Farbe berücksichtigt außerdem `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb` und ob die Ausgabe ein TTY ist. |
| `--verbose`  | Gibt den Stack eines unerwarteten Fehlers aus. Ohne es gibt der Catch auf oberster Ebene eine einzeilige Fehlermeldung aus.       |
| `--help`     | Gibt die Verwendung des Befehls aus.                                                                                              |

`emet --version` gibt die Version aus; `emet --version --json` gibt `{"ok": true, "data": {"version": ...}, "error": null}` aus. Unter `--json` beendet ein fehlschlagender Befehl mit seinem üblichen Exit-Code und gibt `ok: false` aus, mit einem Fehler-`code` aus `findings`, `usage`, `internal`, `slice-timeout`, `expired`, `bad-range` oder `exit-<n>`; was der Befehl auf stdout ausgegeben hat, ist das `data` des Envelopes.

Auf einem TTY gibt `emet` eine einzeilige Meldung auf stderr aus, wenn ein neueres Release bekannt ist. Es prüft höchstens einmal täglich, speichert die Antwort zwischen, wartet nie auf das Netzwerk und bleibt unter `--json` oder ohne TTY stumm.

## Umgebungsvariablen

Für Nutzer gedachte Variablen. Eine gesetzte Variable überschreibt den passenden Konfigurationswert.

| Variable                      | Wirkung                                                                                                                                                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `EMET_SKIP_DEPENDENCY_CHECKS` | `EMET_SKIP_DEPENDENCY_CHECKS=1 emet preflight` stuft eine Abhängigkeitssperre für diesen einen Lauf zu einer Warnung herab. In der eigenen Shell setzen, nicht in etwas, das der Koordinator unbeaufsichtigt ausführt. |
| `EMET_MAX_LIVE_WORKERS`       | Überschreibt [`concurrency.maxLiveWorkers`](configuration.md#concurrency); akzeptiert eine positive ganze Zahl oder `auto`.                                                                                            |
| `EMET_RUN_IDLE_THRESHOLD_MS`  | Überschreibt [`concurrency.runIdleThresholdMs`](configuration.md#concurrency), in Millisekunden.                                                                                                                       |
| `EMET_STATE_DIR`              | Hostweites Zustandsverzeichnis, das den Worker-Slot-Pool enthält. Auflösungsreihenfolge: `$EMET_STATE_DIR`, dann `$XDG_STATE_HOME/emet`, dann `~/.local/state/emet`.                                                   |
| `EMET_MEM_RESERVE_GIB`        | Speicherreserve in GiB, die frei bleiben muss; ein Acquire wird abgelehnt, wenn der verfügbare Speicher darunter liegt. Standard 8. Sie fließt auch in die `auto`-Worker-Obergrenze ein.                               |
| `EMET_MEM_PER_WORKER_GIB`     | Speicher in GiB, der pro Worker angenommen wird, wenn `maxLiveWorkers` den Wert `auto` hat. Standard 2. Erhöhen bei einem schwereren Stack pro Worker, etwa einer browsergesteuerten E2E-Suite pro Worktree.           |
| `EMET_CPU_OVERSUBSCRIBE`      | CPU-Multiplikator für die `auto`-Worker-Obergrenze. Standard 1.                                                                                                                                                        |
| `EMET_AGENT_HOST`             | `codex` lässt `emet guard` die Hook-Eingabe von Codex lesen. Wird von den Codex-Hooks gesetzt; unter Claude Code ungesetzt lassen.                                                                                     |

Die `auto`-Obergrenze ist `clamp(min(cpuCount × EMET_CPU_OVERSUBSCRIBE, floor((memTotal − EMET_MEM_RESERVE_GIB) / EMET_MEM_PER_WORKER_GIB)), min, max)`. Die veralteten `FORGE_*`-Namen werden weiterhin gelesen; `EMET_*` hat Vorrang, wenn beide gesetzt sind.
