Cada subcomando de `emet`, la tabla de compuertas y registros, los códigos de salida y las variables de entorno. Los términos siguen [GLOSSARY.md](../../GLOSSARY.md). Volver al [README](../../README.md). Cada comando imprime su uso con `--help`.

## Subcomandos

Tres comandos de barra envuelven la CLI dentro de Claude Code: `/emet:run` (el pipeline), `/emet:init` (`emet init`) y `/emet:doctor` (`emet doctor .`). En Codex son las skills `$emet:run`, `$emet:init` y `$emet:doctor`. Un `emet` en una terminal normal requiere `install.sh`; de lo contrario, ejecuta `! emet <subcommand>` dentro de una sesión.

`emet <command> [...args]`. `emet --version` imprime la versión.

### Configuración y auditoría

- `emet migrate [--dry-run]`: renombra un repositorio heredado a los nombres de emet.
- `emet init [--tracker linear|github|local] [--after-spec release|promote|none] [--force]`: detecta automáticamente el gestor de paquetes, la rama troncal, el tipo de tracker y el modo after-spec (consulta [`handoff.afterSpec`](configuration.md#handoff)), establece [`schema.ownedPaths`](configuration.md#schema) cuando encuentra un esquema de Prisma (`prisma/schema.prisma` o una carpeta `prisma/schema/`) o una carpeta de migraciones de Drizzle (`drizzle/` junto a un `drizzle.config.*`), y escribe `emet.config.json` y los archivos `docs/agents/*.md`. `--tracker local` configura el tracker local.
- `emet doctor [--all] [<path> ...]`: auditoría de solo lectura de cualquier cantidad de repositorios a la vez; por defecto, el directorio actual. Para un repositorio que configura [`verify.browser`](configuration.md#verify) también informa un hallazgo opcional sobre `agent-browser`: un binario ausente es `indeterminate` (una línea `optional:` con un remedio de instalación), y cuando el binario existe, un `agent-browser doctor` que falla aparece como advertencia. Ninguno es nunca un error, y ninguno cambia el código de salida. Un repositorio sin `verify.browser` no muestra nada.
- `emet setup [--yes] [--with <ids>] [--list] [--json]`: ofrece las instalaciones opcionales con preguntas de readline: `mattpocock-skills` (activado por defecto), `engram`, `mascot`, `orca-pet`, `gh-auth`, `agent-browser` (desactivado por defecto; ejecuta `bun add -g agent-browser@latest` y luego `agent-browser install`, escribe `~/.agent-browser/config.json` con `contentBoundaries: true` y `maxOutput: 50000` solo cuando ese archivo no existe, luego ejecuta `agent-browser doctor` e imprime una advertencia si falla; nunca fija una versión y nunca pasa `--with-deps`, así que si faltan bibliotecas del sistema imprime el comando para que lo ejecutes tú), `context7` (desactivado por defecto; ejecuta `bun add -g ctx7@latest`, luego `ctx7 setup --cli --claude --yes` y `ctx7 setup --cli --codex --yes` solo si `codex` está en el PATH; instala la CLI `ctx7` y su skill `find-docs`, no el servidor MCP, nunca fija una versión e imprime el comando para ejecutar a mano cuando falla un paso de `ctx7 setup`; `ctx7` envía eventos de uso anónimos salvo que se defina `CTX7_TELEMETRY_DISABLED=1`, y un `CONTEXT7_API_KEY` en el entorno tiene prioridad sobre la cuenta guardada por `ctx7 login`), `firecrawl-local` (desactivado por defecto; requiere `cargo`, ejecuta `cargo install firecrawl-local` cuando falta el binario y luego registra un servidor MCP de Claude Code de ámbito de usuario con `FIRECRAWL_CLOUD=search` y `--public-only`, reemplazando un registro anterior con otros ajustes: scrape, crawl y map se ejecutan en la máquina, solo la búsqueda web va a Firecrawl Cloud y se bloquean las direcciones privadas. Pasa el Chrome más reciente que descargó `agent-browser` como `FIRECRAWL_CHROME_PATH`; en Linux, donde AppArmor restringe los espacios de nombres de usuario sin privilegios, imprime un perfil de AppArmor y los comandos `sudo` para cargarlo, porque Firecrawl Local nunca ejecuta Chrome sin su sandbox. Sin un Chrome utilizable, las páginas que se renderizan con JavaScript llegan vacías) y los ajustes recomendados de Claude Code (`claude-settings`, aplicados solo si se eligen, tras una copia de seguridad con marca de tiempo de `settings.json`). Sin TTY, o con `--yes` o `--with`, no pregunta nada e instala exactamente los elementos indicados; sin TTY y sin `--with` no instala nada e imprime el catálogo de `--list`. Cada paso informa `installed`, `already-present`, `skipped` o `failed`; un fallo no detiene a los demás, y el código de salida es 1 si alguno falló. `/emet:setup` es la entrada del plugin y plantea las mismas opciones con `AskUserQuestion`.
- `emet fleet list [--root <dir>] [--json]`: lista los repositorios git con un `emet.config.json` un nivel por debajo de `--root` (por defecto `~/code`), con `tracker.kind`, `handoff.autoChain` y `models.worker`. `emet fleet set <key> <value> [--root <dir>] [--dry-run]` cambia una clave de configuración en cada repositorio listado, validando antes con el cargador de configuración (un valor no válido no cambia nada y sale con 1). `emet fleet launch --feature <text> [--root <dir>] [--repos <a,b>] [--dry-run]` abre una sesión `/emet:run --draft <text>` en cada repositorio tras las comprobaciones de preparación de `emet chain`. `[--dry-run]` imprime los lanzamientos planificados sin iniciar ninguna sesión. Consulta la [guía de fleet](../guide/fleet.md).
- `emet preflight [--run <id>] [--post-dispatch]`: confirma que el repositorio está listo para despachar.
- `emet skill-path <name>`: imprime la ruta absoluta del `SKILL.md` de una skill de mattpocock-skills. Termina con código 1 si no se encuentra la skill.
- `emet selftest`: ejecuta las pruebas unitarias propias de la CLI. Solo en instalaciones desde el código fuente; un binario compilado termina con código 1 y te indica que ejecutes `emet doctor`.

En cualquier repositorio git:

```bash
emet init          # autodetects package manager, trunk branch, tracker kind
emet preflight      # confirms the repo is dispatch-ready
```

`emet init` deja un marcador `TODO(emet):` en los archivos `docs/agents/*.md` generados para todo lo que no puede inferir por sí mismo (un bloqueo compartido de la base de datos de pruebas, la propiedad del esquema, etc.). Complétalos; `emet preflight` se niega a despachar mientras quede alguno.

Luego, dentro de Claude Code (en Codex, usa `$emet:run` con los mismos argumentos):

```text
/emet:run <describe the feature>              # interview → wave 1; later waves via --dispatch/autoChain
/emet:run --draft <describe the feature>      # stop after tickets are created
/emet:run --dispatch <spec-id>                # dispatch a --draft'd spec later
```

#### Revisión de flota

`emet doctor` audita varios repositorios a la vez, en modo de solo lectura:

```bash
emet doctor ~/code/*
```

Informa, por repositorio: un `emet.config.json` válido, los cuatro archivos `docs/agents/*.md` presentes, cero marcadores `TODO(emet):` pendientes, si los comandos de `commands.selfCheck` realmente se resuelven y los hallazgos de dependencias propios del tracker de ese repositorio (`gh`, Linear; consulta [dependencias](dependencies.md#qué-comprueba-cada-cosa)). El plugin mattpocock-skills y las banderas de las CLI externas (`gh`, más las del Agent host: `claude --bg` y `claude agents --json` en Claude Code, `codex exec --json` y `--output-schema` en Codex, verificadas mediante `--help`) se comprueban una sola vez para todo el barrido, no por repositorio.

### Ejecuciones, workers y slots

- `emet claims --reserve <ticket> --run <id> --anchor <pid>`: reserva un ticket para una ejecución. `--release <ticket>`, `--list` y `--prune [--dry-run]` liberan una reclamación, listan las reclamaciones o purgan las obsoletas.
- `emet slots --acquire --run <id> --anchor <pid> --ticket <ticket>`: toma un slot de worker del pool de todo el host en `~/.local/state/emet/slots`. `--release --run <id>`, `--release-index <index>` y `--list` liberan slots o los listan.
- `emet cleanup [--run <id> | --all] [--dry-run] [--force]`: sin argumentos, recupera las ejecuciones cerradas o muertas cuyo trabajo ya aterrizó; `--run` limpia esta ejecución; `--all` es un barrido de ramas de todo el repositorio. Tras un merge, `emet cleanup --run <runId>` libera las ramas, las reclamaciones de tickets y los slots de workers de la oleada. En todos los modos también elimina cada rama local cuyo PR se fusionó en el commit de la punta de la rama, junto con el worktree de agente limpio y sin bloqueo que la contiene.
- `emet lock-reason --run <id> --ticket <ticket> [--anchor <pid>]`: imprime el motivo de `git worktree lock` que un worker escribe al arrancar.
- `emet launch <spec-id> --wave <n>`: en Claude Code, inicia una oleada como una sesión `claude --bg` y abre su pestaña de Orca según `handoff.launcher` (en Codex consulta [Host de Codex](#host-de-codex)). Hace todo el lanzamiento (comprobación de sesión duplicada, `claude --bg`, pestaña) e imprime `{ name, id, attach, orcaTab: { opened, reason } }`. Úsalo, y no un `claude --bg` a secas, siempre que quieras una oleada en otra sesión a mano.
- `emet chain --ticket <id> --spec <id> --wave <n> [gate flags]`: ejecuta `emet gate` con los flags de la compuerta que reciba e inicia la siguiente oleada solo cuando la decisión es `chain`. Antes de lanzar comprueba la preparación (margen de memoria del host, disco e inodos libres en el repo y en `/tmp`, la CLI `orca`) y después confirma que la sesión hija aparece en la lista. Cualquier otra decisión, un problema de preparación bloqueante (`low-memory`, `low-disk`, `low-inodes`, `orca-unavailable`) o una sesión ya existente para la misma especificación y oleada termina con salida 1 con los motivos y no lanza nada.
- `emet status [--spec <id>] [--brief]`: Working / Checking / Ready / Needs-decision por oleada como JSON más una línea de resumen. `--brief` imprime como máximo tres líneas: el estado general, lo que espera a una persona (si hay algo) y la siguiente acción. `emet status --help` documenta el JSON.
- `emet run current [--json]`: imprime la ejecución activa del repo (id de ejecución, spec, oleada, fase y última actualización), leída de `.emet/phase.json`. Sin ejecución activa imprime `no active run` y termina con 0.
- `emet insights [--since <iso|7d|30d>] [--repo <path>] [--all] [--json] [--mark-baseline]`: lee el [diario de eventos](../guide/journal.md) e informa de ejecuciones por origen (humano o auto), decisiones del gate por decisión y motivo, intervenciones humanas por ejecución, resultados de lanzamiento y tickets cerrados. Las líneas ilegibles se omiten y se cuentan. `--mark-baseline` añade una línea base; los informes posteriores cubren solo los eventos posteriores a ella salvo que se indique `--all`. Un diario vacío o inexistente imprime un informe en cero y termina con 0.
- `emet usage [--session <id> | --file <path>] [--stalled [--minutes N]] [--project-dir <path>]`: informa del uso de la sesión; `--stalled` lista los workers detenidos.
- `emet handoff --check <path> | --render <path>`: valida o renderiza la nota `.emet/handoff-<ticket>.md` de un worker.
- `emet metrics [--run <id>]`: informa tokens, costo equivalente en API y tiempo de reloj por ticket, por oleada y por ejecución, leídos de las transcripciones de sesión. También compara el presupuesto de contexto estimado por ticket con lo que realmente usó cada worker. Su resumen va al final del informe final de la ejecución.

### Planificación, revisión y aterrizaje

- `emet promote --spec <id> [--dry-run] [--no-promote] [--hold]`: el paso after-spec, según [`handoff.afterSpec`](configuration.md#handoff). En modo `promote` abre un pull request de `develop` a `main` titulado `chore: 🔖 promote develop`, espera con `emet ci --pr <n> --wait`, lo fusiona con un commit de merge solo cuando el estado es `pass`, y luego, solo si `develop` está por detrás de `main`, abre un pull request de sincronización de `main` a `develop`, espera sus checks del mismo modo y lo fusiona con un commit de merge solo cuando el estado es `pass`; un pull request de sincronización cuyo estado es `fail`, `timeout` o `env-fault`, o cuya fusión es rechazada, queda abierto y nunca cambia el resultado de promote. Añade al diario un evento `promote` con el número del pull request, `merged`, `syncPrNumber`, `syncMerged`, `syncReason`, `rule` y `reason`. `afterSpec` puede ser una lista de reglas; el modo se elige entonces a partir de las rutas que traería promover `develop` (consulta [`handoff.afterSpec`](configuration.md#handoff)), y un `git fetch` o `git diff` que falle hace que el comando salga con 1 antes de abrir ningún pull request. El resultado impreso incluye `rule` (el índice de la regla coincidente, o `null` para la forma de cadena o sin coincidencia), `reason`, `syncPrNumber` (`null` cuando no se abrió ningún pull request de sincronización), `syncMerged` y `syncReason` (una frase que explica por qué un pull request de sincronización quedó abierto; si no, `null`) y `deployCheck: { run, reason }`, que indica si el coordinador debe ejecutar `emet deploy-check`. En modo `release` no fusiona nada y deja el pull request de release a una persona. Con `afterSpec` `none`, con `--no-promote`, o cuando la última oleada de la especificación quedó abierta o marcada, sale con 0 y una nota `skipped`; aun así se ejecuta tras una última oleada limpia para que el resultado incluya la decisión `deployCheck` (en el trunk `main` el deploy check se ejecuta sea cual sea el modo). Un CI que no sea `pass` no fusiona nada y sale con 1. `--dry-run` no abre ningún pull request. `emet promote --spec <id> --hold` escribe el marcador `<run dir>/runs/<id>/no-promote` e imprime `{"held":true}`; mientras exista, `emet promote --spec <id>` sale con 0 y una nota `skipped` sin abrir ningún pull request, así `--no-promote` persiste entre las sesiones de una especificación.
- `emet deploy-check [--json]`: ejecuta `deploy.check.command` hasta que sale con 0, hasta `retries` intentos o `timeoutSeconds`, esperando `intervalSeconds` entre ellos, e imprime `state: ok | failed | timeout` con `attempts`. Salida `0` ok, `1` failed, `3` timeout. Sin `deploy.check` configurado sale con 0 y `skipped: "no deploy check configured"`. El coordinador lo ejecuta solo cuando el resultado de `emet promote` tiene `deployCheck.run` en true. Consulta [`deploy`](configuration.md#deploy).
- `emet validate --spec <id> | --file <path>`: validación del plan; consulta [Compuertas y registros](#compuertas-y-registros).
- `emet surfaces --check <file.json | ->`: rechaza globs de superficies permitidas que se solapen entre los tickets de una oleada.
- `emet approve --run <id>`, `emet materialize-log`, `emet results`, `emet verify`, `emet review-package`, `emet review`, `emet gate`: consulta [Compuertas y registros](#compuertas-y-registros).
- `emet assess --base <ref> --head <ref>`: clasifica un diff como `passive`, `medium` o `high` e imprime JSON con el nivel, los motivos y el modelo y esfuerzo recomendados para el revisor, además de `browserVerify: { run, reason }`: `run` es `true` solo cuando el nivel tiene revisor, [`verify.browser`](configuration.md#verify) está configurado, el binario `agent-browser` está en el PATH y, si `paths` está definido, coincide una ruta modificada; en caso contrario, `reason` nombra la primera condición que falló. Consulta [Models & effort](../../README.md#models--effort) y [`review`](configuration.md#review).
- `emet land --spec <s> --branch <integration> --tickets <id,...>`: fusiona una rama de integración en la rama troncal local (`landing.mode` `merge`). `commands.selfCheck` hace las veces de CI y no se hace push de nada.
- `emet spec-merge --spec <id>`: después de que una oleada se fusiona automáticamente, fusiona los deltas de requisitos `ADDED`/`MODIFIED`/`REMOVED` de la spec en `docs/specs/<area>.md` (`specs.dir`). Comprueba todas las áreas antes de escribir nada. Un conflicto, o un requisito que perdería un escenario, termina con código 1 y deja todos los archivos intactos.
- `emet map [--refresh]`: escribe un resumen de una base de código existente (stack, estructura, convenciones, pruebas, puntos calientes) en `docs/agents/codebase.md` (`map.path`), sellado con el SHA del commit a partir del cual se construyó. El mismo commit siempre produce el mismo archivo. `emet map --stale` termina con código 1 cuando HEAD ha avanzado más allá del sello, y `emet preflight` avisa en ese caso. `emet map --for <globs>` imprime solo las secciones que coinciden con las superficies de edición de un ticket; esa salida es la única parte del mapa que incluye el brief de un worker.
- `emet tracker create-spec|create-ticket|read|frontier|set-state|comment|close`: el tracker local sobre `.scratch/`, JSON por stdout. Consulta [Tracker local](#tracker-local).
- `emet guard`: el hook `PreToolUse` de Claude Code; lee el JSON del hook por stdin (la forma de Codex está en [Host de Codex](#host-de-codex)). `install.sh` lo conecta en `~/.claude/settings.json`. Bloquea un puñado de desencadenantes conocidos de fallos en ejecuciones sin supervisión (consulta `emet/src/guard.ts`).

### Tracker local

Con `tracker.kind: "local"`, las specs y los tickets son archivos markdown bajo `.scratch/` del worktree principal (sin versionar): `.scratch/<slug>/spec.md` y `.scratch/<slug>/issues/<NN>-<slug>.md`, cada uno con líneas `Status:` y `Blocked by:` y comentarios bajo `## Comments`. El coordinador los lee y escribe mediante `emet tracker` (`create-spec`, `create-ticket`, `read`, `frontier`, `set-state`, `comment`, `close`). `emet init --tracker local` lo configura. Consulta el [ADR-0011](../adr/0011-local-tracker-scratch-convention.md).

`landing.mode` es `"pr"` (por defecto) o `"merge"`, independiente del tracker. En modo `merge` una oleada aterriza como un único merge local en la rama troncal con `emet land`, con `commands.selfCheck` en lugar de la CI y sin push. `gh` solo es obligatorio cuando el tracker es `github` o el aterrizaje es `pr`. Consulta el [ADR-0010](../adr/0010-local-merge-landing.md) y [`landing`](configuration.md#landing).

### PRs de aterrizaje y encadenamiento de oleadas

Una oleada es un PR. Su cuerpo lleva una línea `Closes #N` por cada ticket (la palabra clave de cierre del tracker), y el coordinador mueve los tickets a en revisión cuando abre el PR. Después el PR se fusiona según `pr.autoMerge`, o se deja abierto cuando la oleada fue marcada, `autoMerge` es `false` o se agotaron las correcciones de CI (entonces el PR recibe la etiqueta de decisión humana). Las oleadas posteriores se ejecutan en sus propias sesiones, nunca en la que ejecutó la oleada 1. Las secciones `pr` y `handoff` controlan lo que ocurre después; consulta [`pr`](configuration.md#pr) y [`handoff`](configuration.md#handoff).

`emet ci --pr <n> --wait [--rerun-flakes] [--timeout-minutes <m>]` consulta los checks del PR hasta que terminan o se cumple el tiempo límite (por defecto 30). Con `--rerun-flakes` vuelve a ejecutar una vez cada check fallido mediante `gh run rerun --failed`; un check que pasa en la repetición es un Flake. Imprime `state: pass | fail | env-fault | timeout`, los checks fallidos y `flakeReruns`, y nunca fusiona. Un PR sin checks es `pass` con `noChecks: true`. Salida `0` pass, `1` fail o env-fault, `3` timeout. `env-fault` significa checks que terminaron en `STARTUP_FAILURE` o que permanecieron en cola demasiado tiempo: una CI que nunca se ejecutó, no un fallo de código.

Con `tracker.kind: "github"`, `emet tracker close <ticket>... [--pr <n>]` cierra cada ticket (`CLA-<n>`, `#<n>` o un número sin más) con `gh issue close --reason completed`, verifica su estado e informa `closed` o `already-closed`. `--pr` añade el comentario "Landed in #<n>". Después, para cada padre distinto de un ticket `closed` o `already-closed`, lee `gh issue view <spec> --json state,subIssuesSummary`; si la spec está abierta y `subIssuesSummary.completed` es igual a un `total` distinto de cero, cierra la spec con `gh issue close --reason completed` y el comentario "All <total> tickets landed.", y luego verifica su estado. La salida añade `specs`, un `{ spec, outcome, detail? }` por cada padre distinto con resultado `closed`, `open`, `already-closed` o `failed`; un ticket sin padre no añade ninguno, y una lectura o cierre de spec fallido nunca cambia el resultado de un ticket. Termina con `1` si algún ticket o spec falló, después de procesar el resto. Los tickets de Linear los confirma como Done el coordinador mediante el MCP de Linear.

### Host de Codex

Estos comandos sirven al host de agente Codex (`agentHost` `"codex"`); consulta la [guía de Codex](../guide/codex.md).

- `emet dispatch --role worker --run <id> --ticket <id> --prompt-file <file> [--model <m>] [--effort <e>] [--root <dir>]`: tras comprobar la reserva y el slot, crea `.emet/worktrees/agent-<ticket>`, construye una capa `CODEX_HOME` por ejecución e inicia el worker como un `codex exec` desacoplado. `emet dispatch --wait --run <id> --ticket <id> [--timeout <s>]` espera a que termine e imprime el estado de resultado registrado.
- `emet review-run --run <id> --ticket <id> --package <file> --tier <medium|high|passive> [--browser-verify true|false]`: ejecuta el revisor como un `codex exec` de solo lectura sobre un paquete de `emet review-package` e imprime el JSON de hallazgos para `emet review --findings`. El nivel `passive` no inicia ningún proceso. `--browser-verify` es `false` por defecto; con `true` el prompt termina con el eje Browser, con `--session review-<run>` rellenado desde `--run`, de modo que el revisor de Codex verifica la UI como lo hace el revisor de Claude (pásalo cuando `emet assess` imprimió `browserVerify.run: true`; consulta [`verify`](configuration.md#verify)). Sin el flag el prompt no cambia, y un valor distinto de `true` o `false` sale con código 2 y la línea de uso.
- `emet launch <spec-id> --wave <n>`: en este host, inicia un `codex exec` desacoplado que ejecuta `$emet:run --dispatch <spec>` y registra su id de hilo. No se abre ninguna pestaña de Orca, y `codex exec resume <id>` continúa la sesión.
- `emet guard`: con `EMET_AGENT_HOST=codex` lee la entrada de hooks de Codex, comprueba las rutas de `apply_patch` contra `.emet/surface.json` y mantiene cerrada la puerta de aprobación hasta una línea de prompt `approve <id>`.

## Compuertas y registros

Las fases no deciden por sí solas cuándo un ticket está terminado, es fusionable o vale la pena reintentarlo. Llaman a un comando de la CLI que lee un registro en disco e imprime la decisión. Los registros de ejecución viven en `.emet/runs/<run-id>/` y el libro de revisión en `.emet/review/`, en el checkout principal, no en el worktree de un worker.

| Paso                   | Comando                                              | Qué hace cumplir                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Antes de la aprobación | `emet validate --file <plan.json>`                   | Cada `S#` está cubierto por al menos un ticket y tiene un escenario de aceptación. Cada ticket cubre al menos un `S#`. Las superficies de edición son disjuntas dentro de una oleada. No hay ciclos de dependencia. Con [`validate.coupledSurfaces`](configuration.md#validate), un error `coupled-surface-split` cuando un ticket que toca el `source` de un par está en una oleada anterior a la de un ticket que toca sus `dependents` (código de salida 1). `emet preflight` lo ejecuta de nuevo sobre el plan aprobado.                                      |
| Aprobación             | `emet approve --run <id> --spec <file>`              | Escribe `approval.json` con los hashes de la spec y de la lista de tickets. El despacho se niega si alguno cambió después (`--check`).                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Creación de tickets    | `emet materialize-log --run <id> --record/--lookup`  | Guarda el ID de cada ticket creado en cuanto existe, de modo que una ejecución interrumpida nunca crea duplicados.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Worker terminado       | `emet results --run <id> --write/--read <ticket>`    | Los workers escriben un archivo de resultado local (`DONE`, `DONE_WITH_CONCERNS`, `BLOCKED` o `NEEDS_CONTEXT`, más una línea `Risk:`). Solo el coordinador escribe en el tracker.                                                                                                                                                                                                                                                                                                                                                                                 |
| Después de cada worker | `emet verify <ticket> --run <id>`                    | Comprueba que existan commits más allá de la base del despacho, que cada ruta modificada esté dentro de las superficies de edición del ticket, que la nota de handoff pase `handoff --check` y que `commands.workerScopedSuite` pase. La revisión y el merge rechazan un ticket sin registro de aprobación.                                                                                                                                                                                                                                                       |
| Entrada de la revisión | `emet review-package <base> <head> --out <file>`     | Empaqueta el diff para el revisor, que lo recibe como una ruta de archivo. Termina con código 3 si el rango está vacío o no es descendiente de la base.                                                                                                                                                                                                                                                                                                                                                                                                           |
| Revisión               | `emet review --ticket <t> --findings <file>`         | Mantiene el libro de hallazgos y hace cumplir el orden de triaje (`intent_gap` → `bad_plan` → `patch` → `defer`) y el tope de rondas. `--recheck --verdicts <file>` cierra una ronda de corrección: solo se evalúan los hallazgos abiertos cuando empezó, un hallazgo pasa a `resolved` solo mediante un veredicto, y el recheck cuenta contra `budgets.fixRounds` (salida 1 nombrando el tope cuando se agota). `--escalate` pasa al siguiente nivel de modelo. `--rule`/`--rulings` registran y listan los "Rulings I made" para el informe y el cuerpo del PR. |
| Merge o encadenamiento | `emet gate <ticket> --tier … --ci … --integration …` | Imprime `merge`, `hold`, `chain`, `stop` o `defer` como JSON con sus motivos. Lee el registro de verify, los hallazgos abiertos, el nivel de riesgo, la CI, la suite de integración y los presupuestos. Un `hold` incluye `next`: `fix-findings`, `rerun-failed-specs`, `rerun-ci` o `report-infrastructure`. `--no-record` mantiene la decisión fuera del diario. Consulta [`gate`](configuration.md#gate).                                                                                                                                                      |

Después de fusionar las ramas de una oleada, `commands.fullSuite` se ejecuta una vez en la rama de integración. Una ejecución en rojo bloquea el PR y `autoChain`. La compuerta recibe el resultado como `--integration`. Para los presupuestos que lee la compuerta, consulta [`budgets`](configuration.md#budgets).

## Códigos de salida

Los códigos de salida tienen el mismo significado en todos los subcomandos.

| Código | Significado                                                                                               |
| ------ | --------------------------------------------------------------------------------------------------------- |
| `0`    | Limpio.                                                                                                   |
| `1`    | Hallazgos sobre los que actuar.                                                                           |
| `2`    | Error de configuración o de uso; la herramienta nunca llegó a ejecutarse. También un comando desconocido. |
| `3`    | Error interno.                                                                                            |

Un flag desconocido también termina con `2` y nombra el flag. Ctrl-C termina con `130`.

## Flags globales

Todos los comandos los aceptan; los flags propios de cada comando se listan con `emet <command> --help`.

| Flag         | Efecto                                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| `--json`     | Imprime un único sobre `{ok, data, error: {code, message, fix}}` en stdout, también para `--help` y `--version`.   |
| `--no-color` | Desactiva el color ANSI. El color también respeta `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb` y si la salida es un TTY. |
| `--verbose`  | Imprime la traza de un error inesperado. Sin él, el catch de nivel superior imprime un error de una línea.         |
| `--help`     | Imprime el uso del comando.                                                                                        |

`emet --version` imprime la versión; `emet --version --json` imprime `{"ok": true, "data": {"version": ...}, "error": null}`. Bajo `--json`, un comando que falla termina con su código habitual e imprime `ok: false` con un `code` de error entre `findings`, `usage`, `internal`, `slice-timeout`, `expired`, `bad-range` o `exit-<n>`; lo que el comando imprimió en stdout es el `data` del sobre.

En un TTY, `emet` imprime un aviso de una línea en stderr cuando se conoce una versión más reciente. Comprueba como máximo una vez al día, guarda la respuesta en caché, nunca espera a la red y permanece en silencio bajo `--json` o sin TTY.

## Variables de entorno

Variables de cara al usuario. Una variable, cuando está definida, reemplaza el valor de configuración correspondiente.

| Variable                      | Efecto                                                                                                                                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `EMET_SKIP_DEPENDENCY_CHECKS` | `EMET_SKIP_DEPENDENCY_CHECKS=1 emet preflight` degrada un bloqueo por dependencias a una advertencia solo en esa ejecución. Defínela en tu propia shell, no en nada que el coordinador ejecute sin supervisión. |
| `EMET_MAX_LIVE_WORKERS`       | Reemplaza [`concurrency.maxLiveWorkers`](configuration.md#concurrency); acepta un entero positivo o `auto`.                                                                                                     |
| `EMET_RUN_IDLE_THRESHOLD_MS`  | Reemplaza [`concurrency.runIdleThresholdMs`](configuration.md#concurrency), en milisegundos.                                                                                                                    |
| `EMET_STATE_DIR`              | Directorio de estado de todo el host, que contiene el pool de slots de workers. Orden de resolución: `$EMET_STATE_DIR`, luego `$XDG_STATE_HOME/emet`, luego `~/.local/state/emet`.                              |
| `EMET_MEM_RESERVE_GIB`        | Margen de memoria en GiB que debe seguir libre; una adquisición se deniega cuando la memoria disponible está por debajo. Por defecto 8. También alimenta el tope `auto` de workers.                             |
| `EMET_MEM_PER_WORKER_GIB`     | Memoria en GiB que se supone por worker cuando `maxLiveWorkers` es `auto`. Por defecto 2. Súbela para un stack más pesado por worker, como una suite E2E con navegador por worktree.                            |
| `EMET_CPU_OVERSUBSCRIBE`      | Multiplicador de CPU para el tope `auto` de workers. Por defecto 1.                                                                                                                                             |
| `EMET_AGENT_HOST`             | `codex` hace que `emet guard` lea la entrada de hooks de Codex. Lo definen los hooks de Codex; déjala sin definir en Claude Code.                                                                               |

El tope `auto` es `clamp(min(cpuCount × EMET_CPU_OVERSUBSCRIBE, floor((memTotal − EMET_MEM_RESERVE_GIB) / EMET_MEM_PER_WORKER_GIB)), min, max)`. Los nombres heredados `FORGE_*` aún se leen; `EMET_*` gana cuando ambos están definidos.
