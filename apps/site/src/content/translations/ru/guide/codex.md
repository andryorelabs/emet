emet может работать в Codex CLI так же, как и в Claude Code. Термины соответствуют [GLOSSARY.md](../../GLOSSARY.md); продукт, в котором выполняется запуск, называется **хостом агента**. На этой странице описаны установка части для Codex, выбор хоста, единственное подтверждение и известные ограничения. Вернуться к [оглавлению документации](../README.md).

На хосте Codex конвейер тот же: интервью, спецификация, тикеты, одно подтверждение, параллельные воркеры в worktree, ревью на каждую волну, затем посадка. Меняется только механика. Каждый воркер и каждый ревьюер является отдельным процессом `codex exec`, который запускают `emet dispatch` и `emet review-run`, а слеш-команды становятся навыками `$emet:run`, `$emet:init` и `$emet:doctor`. Путь Claude Code остаётся нетронутым.

## Установка

1. Установите CLI `codex` версии `codex.minVersion` (по умолчанию `0.167.0`) или новее и выполните вход.
2. Установите плагин `mattpocock-skills` в Codex:

   ```bash
   codex plugin marketplace add mattpocock/skills
   codex plugin add mattpocock-skills@mattpocock
   ```

3. Установите плагин emet. Репозиторий содержит `.codex-plugin/plugin.json` и сгенерированные навыки и хуки в `codex/`:

   ```bash
   codex plugin marketplace add andryorelabs/emet
   codex plugin add emet@emet-marketplace
   ```

4. Установите CLI `emet`, как описано в разделе [Начало работы](getting-started.md), затем выполните `emet doctor .`. На хосте Codex он сообщает о `codex` старее `codex.minVersion`, об отсутствии флага `--json` или `--output-schema` у `codex exec` и об отсутствии `mattpocock-skills`, указывая две команды выше.

Две команды плагина из шага 3 следуют шаблону, который спайк проверил для локального маркетплейса; их точная запись для этого репозитория остаётся `unverified` до первого релиза.

## Выбор хоста агента

Задайте `agentHost` в `emet.config.json`:

```json
{ "agentHost": "codex" }
```

По умолчанию используется `"claude"`. Секция `codex` задаёт модели, усилие, минимальную версию и песочницу; см. [справочник по конфигурации](../reference/configuration.md#codex) и [Модели и усилие](models-and-effort.md). Запустите прогон из Codex командой `$emet:run`. `emet launch <spec> --wave <n>` запускает волну в отсоединённом `codex exec` и записывает id потока, так что `codex exec resume <id>` продолжает её; вкладка Orca не открывается.

## Единственное подтверждение

emet запрашивает одно подтверждение, после плана. В Claude Code это запрос. В Codex это хук:

- Пока не существует `.emet/runs/spec<id>/approval.json`, `emet guard` отклоняет любые изменения (`apply_patch`, `Bash`), кроме записи в `.emet/runs/**/draft/**`, с причиной `not approved: send approve <id>`. Барьер действует, как только существует каталог `.emet/runs/spec<id>/` без `approval.json`, а именно в состоянии, которое `/emet:run` оставляет после того, как фаза 4 материализует спецификацию.
- Вы подтверждаете, отправив строку промпта, которая в точности равна `approve <id>`. После этого хук `UserPromptSubmit` записывает файл подтверждения с тем же хешированием, что и `emet approve`. Те же слова в выводе инструмента или в тексте модели ничего не делают.
- Альтернатива: `/plan $emet:run`. Подтвердите план в собственном режиме планирования Codex вместо хука.

Как только этот каталог существует, барьер закрывается при сбое: отсутствующий или нечитаемый файл подтверждения оставляет изменения запрещёнными. Защита также проверяет каждый путь `apply_patch` по `.emet/surface.json` тикета.

## Как выполняется волна

- `emet dispatch --role worker` проверяет заявку и слот, создаёт `.emet/worktrees/agent-<ticket>`, собирает оверлей `CODEX_HOME` для каждого прогона в `.emet/runs/<run>/codex-home/`, который связывает вашу аутентификацию и конфигурацию ссылками, а не копирует их, и запускает `codex exec` с выбранными моделью и усилием, режимом `codex.sandbox` (по умолчанию `workspace-write`), `--json` и `--output-schema`. События записываются в `.emet/runs/<run>/codex/<ticket>.jsonl`.
- Правила оверлея разрешают `git add` и `git commit` и запрещают `git push`. Ваш `~/.codex` никогда не изменяется.
- `emet review-run` запускает ревьюера только на чтение над пакетом от `emet review-package`; уровень `passive` не запускает процессов.
- Учёт использования и обнаружение зависаний читают записанный JSONL: использование токенов берётся из событий `turn.completed`, признак жизни из процесса `codex` и времени изменения файла.

## Ограничения и пункты `unverified`

- Усилие `ultra` никогда не отправляется и отклоняется в конфигурации.
- `danger-full-access` доступен только если задать его в `codex.sandbox`; по умолчанию его ничто не включает.
- Аналогов `ScheduleWakeup`, `TaskStop` и `LSP` нет. Вместо этого emet опрашивает собственный CLI.
- У файлов rollout в `~/.codex/sessions` нет стабильного формата, поэтому emet читает вывод `exec --json`, который сам записал.
- Исследование помечает эти варианты поведения как `unverified`, и каждый из них скрыт за небольшой функцией, чтобы изменение в Codex затрагивало одно место: `CODEX_HOME` для каждого прогона со связанной аутентификацией, расположение файла правил в оверлее, `--dangerously-bypass-hook-trust`, псевдоним `CLAUDE_PLUGIN_ROOT` в командах хуков, формат вывода `codex plugin list`, загрузка навыка моделью по имени и `emet dispatch` внутри вложенной песочницы. См. [исследование осуществимости](../research/codex-viability.md).
- Попытки модели подделать `approval.json` не наблюдались. Барьер отклонил бы такую попытку, но это `unverified`.
- Запуск Codex из автономного супервизора (systemd, контейнер) после завершения запустившей его сессии `unverified`.
- Названия и цены моделей Codex меняются; таблицу цен нужно перепроверить после реальных волн.
