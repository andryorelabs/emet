emet может работать в Codex CLI так же, как и в Claude Code. Термины соответствуют [GLOSSARY.md](../../GLOSSARY.md); продукт, в котором выполняется запуск, называется **хостом агента**. На этой странице описаны установка части для Codex, выбор хоста, единственное подтверждение и известные ограничения. Вернуться к [оглавлению документации](../README.md).

На хосте Codex конвейер тот же: интервью, спецификация, тикеты, одно подтверждение, параллельные воркеры в worktree, ревью на каждую волну, затем посадка. Меняется только механика. Каждый воркер и каждый ревьюер является отдельным процессом `codex exec`, который запускают `emet dispatch` и `emet review-run`, а слеш-команды становятся навыками `$emet:run`, `$emet:init` и `$emet:doctor`. Путь Claude Code остаётся нетронутым.

## Установка

1. Установите CLI `codex` версии `codex.minVersion` (по умолчанию `0.167.0`) или новее и выполните вход.
2. Установите плагин `mattpocock-skills` в Codex:

   ```bash
   codex plugin marketplace add mattpocock/skills
   codex plugin add mattpocock-skills@mattpocock
   ```

3. Установите плагин emet. Репозиторий содержит `.codex-plugin/plugin.json` и сгенерированные навыки и хуки в `codex/`:

   ```bash
   codex plugin marketplace add andryorelabs/emet
   codex plugin add emet@emet-marketplace
   ```

4. Установите CLI `emet`, как описано в разделе [Начало работы](getting-started.md), затем выполните `emet doctor .`. `install.sh` также устанавливает команды и агенты Claude Code в `~/.claude`; в Codex это безвредно, и `emet doctor` не предупреждает об одновременном использовании плагина Codex и `install.sh`. На хосте Codex он сообщает о `codex` старее `codex.minVersion`, об отсутствии флага `--json` или `--output-schema` у `codex exec` и об отсутствии `mattpocock-skills`, указывая две команды выше.

Обе команды плагина из шага 3 были запущены на настоящем `codex` (0.167.0): в чистом `CODEX_HOME` они завершаются с кодом 0, а `codex plugin list` показывает `emet@emet-marketplace installed, enabled`. Форма с локальным путём, `codex plugin marketplace add <repo>`, даёт тот же результат.

## Выбор хоста агента

Задайте `agentHost` в `emet.config.json`:

```json
{ "agentHost": "codex" }
```

По умолчанию используется `"claude"`. Секция `codex` задаёт модели, усилие, минимальную версию и песочницу; см. [справочник по конфигурации](../reference/configuration.md#codex) и [Модели и усилие](models-and-effort.md). Запустите прогон из Codex командой `$emet:run`. `emet launch <spec> --wave <n>` запускает волну в отсоединённом `codex exec` и записывает id потока, так что `codex exec resume <id>` продолжает её; вкладка Orca не открывается.

## Единственное подтверждение

emet запрашивает одно подтверждение, после плана. В Claude Code это запрос. В Codex это хук:

- Пока не существует `.emet/runs/spec<id>/approval.json`, `emet guard` отклоняет любые изменения (`apply_patch`, `Bash`), кроме записи в `.emet/runs/**/draft/**`, с причиной `not approved: send approve <id>`. Барьер действует, как только существует каталог `.emet/runs/spec<id>/` без `approval.json`, а именно в состоянии, которое `$emet:run` оставляет после того, как фаза 4 материализует спецификацию.
- Вы подтверждаете, отправив строку промпта, которая в точности равна `approve <id>`. После этого хук `UserPromptSubmit` записывает файл подтверждения с тем же хешированием, что и `emet approve`. Те же слова в выводе инструмента или в тексте модели ничего не делают.
- Альтернатива: `/plan $emet:run`. Подтвердите план в собственном режиме планирования Codex вместо хука.

Как только этот каталог существует, барьер закрывается при сбое: отсутствующий или нечитаемый файл подтверждения оставляет изменения запрещёнными. Защита также проверяет каждый путь `apply_patch` по `.emet/surface.json` тикета.

## Как выполняется волна

- `emet dispatch --role worker` проверяет заявку и слот, создаёт `.emet/worktrees/agent-<ticket>`, собирает оверлей `CODEX_HOME` для каждого прогона в `.emet/runs/<run>/codex-home/` и запускает `codex exec` с выбранными моделью и усилием, режимом `codex.sandbox` (по умолчанию `danger-full-access`), `--json` и `--output-schema`. События записываются в `.emet/runs/<run>/codex/<ticket>.jsonl`. Воркер определяется по `threadId` события `thread.started` и по этому пути JSONL; идентификатор процесса остаётся лишь вспомогательным полем.
- Оверлей генерируется, а не связывается ссылками. Ваш `auth.json` связывается символической ссылкой (никогда не копируется), кэш плагина emet связывается из вашего домашнего каталога Codex, если он существует, а оверлей пишет собственный минимальный `config.toml`: локальный маркетплейс и `[plugins."emet@emet-marketplace"] enabled = true`, таблицу `[projects."<dir>"]` с `trusted` только для собственных каталогов прогона, а также выбранные `model` и `model_reasoning_effort`. Ни ваши таблицы `[projects]`, ни другие настройки не копируются, а ваш `~/.codex` никогда не изменяется.
- Файл `rules/default.rules` оверлея разрешает `git add`, `git commit`, `git status`, `git worktree`, `git -C <dir> ...` и подкоманды `emet` `dispatch`, `review-run`, `launch`, `claims`, `slots`, `results`, `handoff` и `ask`, а `git push` запрещает. Поскольку песочница по умолчанию больше не блокирует запись, `emet guard` также отклоняет любую команду `Bash`, argv которой запускает `git push`, включая `git -C <dir> push` и `git --git-dir=<dir> push`, независимо от песочницы.
- У воркера никогда нет бокового канала к координатору. Он эскалирует через почтовый ящик запуска: `emet ask --run <run> --ticket <ticket> --body <text>` записывает вопрос и печатает его id, а `emet ask ... --wait <n>` опрашивает ответ (код выхода 0 печатает его, 3 означает, что отрезок ожидания истёк, 4 означает, что `budgets.askWaitMinutes` исчерпан, поэтому воркер пишет результат BLOCKED и завершается). Пока у живого воркера есть открытый вопрос, `emet dispatch --wait` печатает `question <ticket> <id>` вместо статуса результата и никогда не классифицирует воркера как зависшего; координатор читает `emet inbox --run <run>`, отвечает через `emet reply --run <run> --ticket <ticket> --id <n> --body <text>` и возобновляет `emet dispatch --wait`. Записанный результат всегда важнее открытого вопроса. См. [ADR-0023](../adr/0023-cli-owned-mailbox-for-codex-workers.md).
- Результаты читаются из `<git-common-dir>/.emet/runs/<run>/results/`, то есть оттуда же, куда пишет `emet results --write`, поэтому воркер в собственном worktree находится.
- `emet review-run` запускает ревьюера только на чтение над пакетом от `emet review-package`; уровень `passive` не запускает процессов.
- Модели выбираются по `models_cache.json` в домашнем каталоге прогона, а если его там нет, то в вашем настоящем домашнем каталоге Codex (только чтение). Настроенный слаг, которого нет в списке, заменяется, и замена записывается в журнал; если ничего выбрать не удалось, `emet review-run` завершается ошибкой до вызова модели, называя роль и перечисленные слаги.
- Учёт использования и обнаружение зависаний читают записанный JSONL: использование токенов берётся из событий `turn.completed`, признак жизни из роста файла, поэтому воркер в другом пространстве имён pid по-прежнему считается живым. `emet preflight` и `emet cleanup` используют одно правило для освобождаемого рабочего дерева без владельца (ветка воркера, тикет влит, чистое дерево, нет чужой блокировки), поэтому preflight советует запустить `emet cleanup`, только когда cleanup действительно что-то сделает.

## Что показал прогон на настоящем Codex

[Отчёт о пробе](../research/codex-probe-report.md) заново прогнал все проверки на `codex-cli 0.167.0` (бесплатный тариф ChatGPT, Linux) после этих изменений. Все прежние строки `failed` теперь `verified`:

- Поток из 2 волн влил в транк настоящие коммиты воркеров Codex: волна 1 через `emet dispatch`, волна 2 из сессии, запущенной командой `emet launch <spec> --wave 2`, которая загрузила `$emet:run` из кэша плагина оверлея. `emet review-run` отработал в каждом потоке.
- Необязательный e2e (`EMET_CODEX_E2E=1`) проходит: воркер делает коммит под `danger-full-access`, а `codex execpolicy check` отвечает `forbidden` для `git push origin develop` и `allow` для `git -C <dir> commit`.
- `~/.codex/config.toml` сохранил ту же sha256 во время пробы, e2e и семи потоков.

## Ограничения и пункты `unverified`

- Усилие `ultra` никогда не отправляется и отклоняется в конфигурации.
- `danger-full-access` — значение `codex.sandbox` по умолчанию для воркеров Codex и `emet launch`, потому что песочница `workspace-write` делает `.git` доступным только для чтения и воркер не смог бы сделать коммит. Задайте `codex.sandbox` равным `"workspace-write"`, чтобы сохранить песочницу; тогда воркеры не смогут делать коммиты. Компромисс записан в [ADR-0022](../adr/0022-codex-workers-run-unsandboxed-by-default.md). Путь Claude его никогда не использует. Без песочницы защитой служат отказ на push в `emet guard` и файл правил.
- Аналогов `ScheduleWakeup`, `TaskStop` и `LSP` нет. Вместо этого emet опрашивает собственный CLI.
- У файлов rollout в `~/.codex/sessions` нет стабильного формата, поэтому emet читает вывод `exec --json`, который сам записал.
- Проверено на настоящем CLI и по-прежнему скрыто за небольшими функциями, чтобы изменение в Codex затрагивало одно место: `CODEX_HOME` для каждого прогона со связанной аутентификацией, файл правил `rules/default.rules`, `--dangerously-bypass-hook-trust`, псевдоним `CLAUDE_PLUGIN_ROOT` в командах хуков, формат вывода `codex plugin list`, загрузка навыка моделью по имени, `emet dispatch` внутри вложенной сессии, попытка модели подделать `approval.json` (отклоняется) и обе формы `codex plugin marketplace add`. См. [исследование осуществимости](../research/codex-viability.md).
- По-прежнему `unverified`: запуск Codex из автономного супервизора под systemd или в контейнере (проверялся только отсоединённый процесс).
- Известные доработки из отчёта о пробе: `emet init` записывает названия моделей Claude в `models` при `agentHost: "codex"`, явный `emet dispatch --model` не сверяется с кэшем, `emet lock-reason` ищет предка `claude`, а тикет, воркер которого умер, нельзя заново отправить в то же рабочее дерево.
- Названия и цены моделей Codex меняются; таблицу цен нужно перепроверить после реальных волн.
