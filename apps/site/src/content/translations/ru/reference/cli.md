Каждая подкоманда `emet`, таблица гейтов и записей, коды завершения и переменные окружения. Термины соответствуют [GLOSSARY.md](../../GLOSSARY.md). Назад к [README](../../README.md). Каждая команда выводит справку по использованию с `--help`.

## Подкоманды

Три слэш-команды оборачивают CLI внутри Claude Code: `/emet:run` (конвейер), `/emet:init` (`emet init`) и `/emet:doctor` (`emet doctor .`). В Codex это навыки `$emet:run`, `$emet:init` и `$emet:doctor`. Для `emet` в обычном терминале нужен `emet self install`; иначе выполняйте `! emet <subcommand>` внутри сессии.

`emet <command> [...args]`. `emet --version` выводит версию.

### Настройка и аудит

- `emet migrate [--dry-run]`: переименовывает устаревший репозиторий под имена emet.
- `emet init [--tracker linear|github|local] [--after-spec release|promote|none] [--force]`: автоматически определяет менеджер пакетов, основную ветку, вид трекера и режим after-spec (см. [`handoff.afterSpec`](configuration.md#handoff)), задаёт [`schema.ownedPaths`](configuration.md#schema), если находит схему Prisma (`prisma/schema.prisma` или папку `prisma/schema/`) или папку миграций Drizzle (`drizzle/` рядом с `drizzle.config.*`), и записывает `emet.config.json` и файлы `docs/agents/*.md`. `--tracker local` настраивает локальный трекер.
- `emet doctor [--all] [<path> ...]`: аудит любого числа репозиториев за раз, только на чтение; по умолчанию текущий каталог. Для репозитория, где настроен [`verify.browser`](configuration.md#verify), он также сообщает необязательную находку об `agent-browser`: отсутствующий бинарный файл даёт `indeterminate` (строка `optional:` с указанием, как установить), а когда бинарный файл есть, неуспешный `agent-browser doctor` отображается как предупреждение. Ни то, ни другое никогда не является ошибкой и не меняет код выхода. Репозиторий без `verify.browser` ничего не показывает.
- `emet setup [--yes] [--with <ids>] [--list] [--json] [--dry-run] [--restore <id>]`: предлагает необязательные установки через запросы readline: `mattpocock-skills` (по умолчанию включено), `engram`, `mascot`, `orca-pet`, `gh-auth`, `agent-browser` (по умолчанию выключено; выполняет `bun add -g agent-browser@latest`, затем `agent-browser install`, записывает `~/.agent-browser/config.json` с `contentBoundaries: true` и `maxOutput: 50000` только если этого файла нет, затем выполняет `agent-browser doctor` и выводит предупреждение, если он завершился ошибкой; никогда не закрепляет версию и никогда не передаёт `--with-deps`, поэтому при нехватке системных библиотек выводит команду, которую нужно выполнить вам), `context7` (по умолчанию выключено; выполняет `bun add -g ctx7@latest`, затем `ctx7 setup --cli --claude --yes`, а `ctx7 setup --cli --codex --yes` только если `codex` есть в PATH; устанавливает CLI `ctx7` и его скилл `find-docs`, а не MCP-сервер, никогда не закрепляет версию и выводит команду для ручного запуска, если шаг `ctx7 setup` завершился ошибкой; `ctx7` отправляет анонимные события использования, если не задано `CTX7_TELEMETRY_DISABLED=1`, а `CONTEXT7_API_KEY` в окружении имеет приоритет над учётной записью, сохранённой через `ctx7 login`), `firecrawl-local` (по умолчанию выключено; требует `cargo`, выполняет `cargo install firecrawl-local`, если бинарного файла нет, затем регистрирует MCP-сервер Claude Code на уровне пользователя с `FIRECRAWL_CLOUD=search` и `--public-only`, заменяя прежнюю регистрацию с другими настройками: scrape, crawl и map выполняются на машине, в Firecrawl Cloud уходит только веб-поиск, а частные адреса блокируются. Он передаёт самый новый Chrome, скачанный `agent-browser`, как `FIRECRAWL_CHROME_PATH`; в Linux, где AppArmor ограничивает непривилегированные пользовательские пространства имён, он выводит профиль AppArmor и команды `sudo` для его загрузки, потому что Firecrawl Local никогда не запускает Chrome без его песочницы. Без пригодного Chrome страницы, которые отрисовываются с помощью JavaScript, приходят пустыми) и рекомендуемые настройки Claude Code (`claude-settings`, применяются только при выборе, после резервной копии `settings.json` с отметкой времени). Без TTY, а также с `--yes` или `--with` ничего не спрашивает и устанавливает ровно указанные пункты; без TTY и без `--with` ничего не устанавливает и выводит каталог `--list`. Каждый шаг сообщает `installed`, `already-present`, `skipped` или `failed`; одна ошибка не останавливает остальные, а код выхода равен 1, если что-то завершилось с ошибкой. `/emet:setup` — это точка входа плагина, он задаёт те же вопросы через `AskUserQuestion`.
- `emet setup --dry-run` (сочетается с `--with`, `--yes` и `--json`): для каждого выбранного элемента печатает запланированные шаги (или `already-present`), используя только проверки без записи, и ничего не выполняет. Команды не запускаются, файлы не записываются, журнал не пишется. Код выхода 0.
- Журнал setup: `setup-ledger.json` лежит в каталоге состояния (`EMET_STATE_DIR`, затем `XDG_STATE_HOME`). Для каждого элемента с результатом `installed` сохраняется запись для отката (`claude-settings` хранит прежний `model`, фактически добавленные deny-правила и путь к резервной копии; `firecrawl-local` хранит прежнюю запись MCP в области пользователя и признак того, запускался ли `cargo install`; плагины хранят id плагина; `orca-pet` хранит записанные файлы; `agent-browser` и `context7` хранят глобальный пакет bun; `engram` хранит формулу brew и плагин). Элемент `already-present` ничего не записывает, а повторный `installed` того же id сохраняет состояние «до» из первой записи. Записи атомарны. Повреждённый журнал не читается как пустой, а приводит к ошибке с указанием его пути.
- `emet setup --restore <id>`: принимает только `claude-settings` и `firecrawl-local`. `claude-settings` после резервной копии с отметкой времени восстанавливает прежний `model` (или удаляет ключ, если его не было) и удаляет только те deny-правила, которые добавил emet. Если текущий `model` не совпадает с тем, что установил setup, он остаётся как есть, и печатается предупреждение. `firecrawl-local` выполняет `claude mcp remove firecrawl-local -s user`, а затем, если запись была сохранена, `claude mcp add-json firecrawl-local '<previous json>' -s user`. Успешное восстановление удаляет запись из журнала. Любой другой id завершается с кодом 2 (ошибка использования), а id без записи в журнале печатает `nothing to restore for <id>` и завершается с кодом 1.
- `emet self install [latest|X.Y.Z] [--dry-run] [--force] [--from <checkout>]`: автономная установка. Помещает бинарный файл в `~/.local/share/emet/versions/<v>/emet` с символической ссылкой `~/.local/bin/emet`, записывает референсные промпты и `.install-manifest.json` в `~/.claude/emet/`, команды в `~/.claude/commands/emet/` и агентов в `~/.claude/agents/`, вносит хуки emet в `~/.claude/settings.json` (с резервной копией, чужие хуки не затрагиваются) и, если Codex присутствует, записывает навыки в `~/.agents/skills` и добавляет хуки в `$CODEX_HOME/hooks.json` (по умолчанию `~/.codex`; `config.toml` никогда не записывается, поэтому один раз подтвердите хуки через `/hooks`). Повторный запуск ничего не меняет; изменённый файл сохраняется, а новая версия ложится рядом как `<file>.new`. `--dry-run` перечисляет все записи и ничего не записывает. Команда отказывается работать, пока установлен плагин emet; `--force` всё равно продолжает. `--from <checkout>` воспроизводит установку из исходников Bun: исходники CLI копируются в `~/.claude/emet`, а `~/.local/bin/emet` становится обёрткой, запускающей их через `bun`, поэтому `emet selftest` работает; без `bun` команда завершается ошибкой. Контрибьюторы используют `emet self install --from .`. Однострочная команда `curl -fsSL https://emet.andryore.dev/install.sh | sh` скачивает бинарный файл релиза, проверяет `SHA256SUMS` и запускает эту команду.
- `emet self update [latest|X.Y.Z]`: скачивает релиз, проверяет `SHA256SUMS` (и аттестацию, если есть `gh`) и подготавливает его. Замена символической ссылки и установленных файлов происходит, только когда не занят ни один слот воркера; иначе обновление остаётся отложенным до следующего запуска сессии. Сбой оставляет текущую версию нетронутой и записывается в журнал. Предыдущая версия сохраняется для отката, более старые удаляются. Для установок плагина команда ничего не делает. `emet self update --auto [off|on]` запускает хук `SessionStart`: не чаще раза в сутки, в отсоединённом режиме и без вывода, если сети нет; `off` или `on` переключает его. `EMET_AUTO_UPDATE=0` тоже отключает его.
- `emet uninstall [--dry-run] [--yes] [--purge] [--json]`: удаляет установку `emet self install` и то, что добавил `emet setup`. Сначала строится весь план, затем он выполняется. Удаляет каждый файл из манифеста установки, текущий хеш которого совпадает с записанным, и его соседа `.new`. Изменённые файлы остаются и перечисляются. Шим `~/.local/bin/emet` удаляется только если это обёртка установки или символическая ссылка на `~/.claude/emet`; затем удаляются манифест и опустевшие каталоги. Шим, указывающий за пределы установки, остаётся и перечисляется. Без манифеста (установка плагином) файлы пропускаются и печатается `claude plugin uninstall emet@emet-marketplace`. Если `codex` есть в PATH, печатается, как удалить плагин Codex. Из `~/.claude/settings.json` удаляются только хуки с командой `emet guard` в любом событии (опустевшие группы и события убираются, все прочие хуки сохраняются, а перед этим делается копия с отметкой времени `.pre-emet-guard-backup.`), а дополнения из журнала откатываются (`claude-settings` и `firecrawl-local` как выше; плагины через `claude plugin uninstall <id>`; файлы `orca-pet` и созданный emet конфиг `agent-browser` удаляются). Для глобальных пакетов brew, bun и cargo команда удаления только печатается и никогда не выполняется, а `gh auth` не затрагивается. Откатанная запись уходит из журнала, и сбой одного дополнения не останавливает остальные. `--dry-run` печатает весь план, ничего не меняет и завершается с кодом 0. `--yes` отключает подтверждение, `--purge` дополнительно удаляет каталог состояния и `~/.emet` (без него оба остаются). При наличии TTY и без `--yes` задаётся один вопрос подтверждения; без TTY и без `--yes` печатается план, ничего не меняется и код выхода 0. Код выхода 1, если какой-либо шаг не удался.
- `emet fleet list [--root <dir>] [--json]`: перечисляет git-репозитории с `emet.config.json` на один уровень ниже `--root` (по умолчанию `~/code`) вместе с `tracker.kind`, `handoff.autoChain` и `models.worker`. `emet fleet set <key> <value> [--root <dir>] [--dry-run]` меняет один ключ конфигурации в каждом перечисленном репозитории, предварительно проверяя его загрузчиком конфигурации (недопустимое значение ничего не меняет и завершается с кодом 1). `emet fleet launch --feature <text> [--root <dir>] [--repos <a,b>] [--dry-run]` открывает сессию `/emet:run --draft <text>` в каждом репозитории после проверок готовности `emet chain`. `[--dry-run]` выводит запланированные запуски, не запуская сессию. См. [руководство по fleet](../guide/fleet.md).
- `emet fleet status [--json]`: читает глобальный журнал и выводит для каждого репозитория последнее состояние каждой сессии за последние 24 часа (кроме `ended`). `--json` выводит `{ repos: [{ repo, sessions: [{ sessionId, state, blocked, since, runId }] }], blocked: <count> }`; без него выводится по одной строке на репозиторий, `<repo>: <b> blocked, <w> working, <i> idle`, сначала репозитории с заблокированными сессиями. Завершается с кодом 0 и при пустом результате. См. [Просмотр заблокированных сессий](../guide/fleet.md#просмотр-заблокированных-сессий).
- `emet preflight [--run <id>] [--post-dispatch]`: подтверждает, что репозиторий готов к диспетчеризации.
- `emet skill-path <name>`: выводит абсолютный путь `SKILL.md` навыка из mattpocock-skills. Завершается кодом 1, если навык не найден.
- `emet selftest`: запускает собственные модульные тесты CLI. Только для установки из исходников; скомпилированный бинарный файл завершается кодом 1 и предлагает выполнить `emet doctor`.

В любом git-репозитории:

```bash
emet init          # autodetects package manager, trunk branch, tracker kind
emet preflight      # confirms the repo is dispatch-ready
```

`emet init` оставляет маркер `TODO(emet):` в сгенерированных файлах `docs/agents/*.md` для всего, что не может определить сам (общая блокировка тестовой базы данных, владелец схемы и так далее). Заполните их; пока остаётся хотя бы один, `emet preflight` отказывается запускать диспетчеризацию.

Затем, внутри Claude Code (в Codex используйте `$emet:run` с теми же аргументами):

```text
/emet:run <describe the feature>              # interview → wave 1; later waves via --dispatch/autoChain
/emet:run --draft <describe the feature>      # stop after tickets are created
/emet:run --dispatch <spec-id>                # dispatch a --draft'd spec later
```

#### Проверка флота

`emet doctor` проверяет несколько репозиториев сразу, только на чтение:

```bash
emet doctor ~/code/*
```

Для каждого репозитория отчёт показывает: корректный `emet.config.json`, наличие всех четырёх файлов `docs/agents/*.md`, отсутствие оставшихся маркеров `TODO(emet):`, действительно ли разрешаются команды из `commands.selfCheck`, а также результаты проверки зависимостей, специфичных для трекера этого репозитория (`gh`, Linear; см. [зависимости](dependencies.md#что-что-проверяет)). Плагин mattpocock-skills и флаги внешних CLI (`gh`, а также флаги хоста агента: `claude --bg` и `claude agents --json` в Claude Code, `codex exec --json` и `--output-schema` в Codex; проверяются через `--help`) проверяются один раз на весь обход, а не для каждого репозитория.

### Запуски, воркеры и слоты

- `emet claims --reserve <ticket> --run <id> --anchor <pid>`: резервирует тикет за запуском. `--release <ticket>`, `--list` и `--prune [--dry-run]` снимают захват, выводят список захватов или удаляют устаревшие.
- `emet slots --acquire --run <id> --anchor <pid> --ticket <ticket>`: берёт слот воркера из общего пула хоста в `~/.local/state/emet/slots`. `--release --run <id>`, `--release-index <index>` и `--list` освобождают слоты или выводят их список.
- `emet cleanup [--run <id> | --all] [--dry-run] [--force]`: без аргументов освобождает ресурсы закрытых или мёртвых запусков, чья работа приземлилась; `--run` очищает этот запуск; `--all` — обход веток по всему репозиторию. После слияния `emet cleanup --run <runId>` освобождает ветки волны, захваты тикетов и слоты воркеров. В любом режиме он также удаляет каждую локальную ветку, PR которой был слит на последнем коммите ветки, вместе с чистым и незаблокированным worktree агента, в котором она находится.
- `emet lock-reason --run <id> --ticket <ticket> [--anchor <pid>]`: выводит причину `git worktree lock`, которую воркер записывает при начальной настройке.
- `emet launch <spec-id> --wave <n>`: в Claude Code запускает волну как сессию `claude --bg` и открывает её вкладку Orca согласно `handoff.launcher` (о Codex см. [Хост Codex](#хост-codex)). Выполняет запуск целиком (проверка дубликатов сессий, `claude --bg`, вкладка) и выводит `{ name, id, attach, orcaTab: { opened, reason } }`. Используйте его, а не голый `claude --bg`, когда нужно вручную запустить волну в другой сессии.
- `emet chain --ticket <id> --spec <id> --wave <n> [gate flags]`: запускает `emet gate` с переданными флагами гейта и стартует следующую волну, только когда решение — `chain`. Перед запуском проверяет готовность (запас памяти хоста, свободное место на диске и inode в репозитории и в `/tmp`, CLI `orca`), а потом убеждается, что дочерняя сессия есть в списке. Любое другое решение, блокирующая проблема готовности (`low-memory`, `low-disk`, `low-inodes`, `orca-unavailable`) или уже существующая сессия для той же спецификации и волны завершает работу с кодом 1 и причинами и ничего не запускает.
- `emet status [--spec <id>] [--brief]`: Working / Checking / Ready / Needs-decision по каждой волне в виде JSON плюс итоговая строка. `--brief` вместо этого выводит не более трёх строк: общее состояние, что ждёт человека (если есть) и следующее действие. `emet status --help` описывает этот JSON. В JSON добавляется `sessions: [{ sessionId, state, blocked, since, runId }]`: последнее событие `session.attention` каждой сессии этого репозитория за последние 24 часа, кроме `ended`. `blocked` равно `state === "needs-decision"`, а `since` это `ts` этого события. Любая заблокированная сессия делает общий `state` равным `needs-decision` (в том числе когда волны нет), строка сводки указывает, сколько сессий заблокировано, а `--brief` перечисляет их в строке о том, что ждёт человека.
- `emet run current [--json]`: выводит активный запуск репозитория (id запуска, спецификацию, волну, фазу и время последнего обновления), прочитанный из `.emet/phase.json`. Без активного запуска выводит `no active run` и завершается с кодом 0.
- `emet memory search --json <query> [--limit <n>]`: ищет в [Engram](https://github.com/Gentleman-Programming/engram) уроки прошлых запусков. Поиск идёт с `match_mode: "any"` (`--limit` по умолчанию 5, максимум 20), оставляет только заметки, чей topic key начинается с `emet/<repo>/lessons/`, и выводит `{available: true, results: [{id, topicKey, title, content}]}`, где `content` обрезан до 2000 символов. `<repo>` — последний сегмент пути из `git remote get-url <repo.remote>` без `.git`, иначе имя каталога основного worktree.
- `emet memory save --json --key <spec-<id>|quick-<runId>> --run <runId> --outcome <landed|chained|hold|stop|blocked>`: читает из stdin от 1 до 5 пунктов-уроков (строки `- ` не длиннее 300 символов каждая) и добавляет их разделом `## <runId> — <outcome> (<date>)` в заметку с topic key `emet/<repo>/lessons/<key>` либо создаёт эту заметку. Заметка длиннее 20000 символов теряет самые старые разделы. Выводит `{available: true, saved: true, topicKey}`.
  - Обе подкоманды обращаются к Engram, запуская `engram mcp --tools=agent` в корне репозитория; плагин Engram не нужен. Они никогда не передают в Engram `project`.
  - Коды выхода: `2` при неверном использовании (нет подкоманды, нет запроса, нет пунктов, больше 5 пунктов, пункт длиннее 300 символов, неизвестный outcome, неверный key). Любая проблема Engram (нет в PATH, неудачный handshake, ошибка инструмента, тайм-аут, некорректный JSON) завершается кодом `0`. До успешного handshake вывод — `{available: false, reason}`; после него — `{available: true, results: [], reason}` для `search` или `{available: true, saved: false, reason}` для `save`. `memory.enabled: "off"` выводит `{available: false, reason: "memory.enabled is off"}` и ничего не запускает. См. [`memory`](configuration.md#memory).
- `emet insights [--since <iso|7d|30d>] [--repo <path>] [--all] [--json] [--mark-baseline]`: читает [журнал событий](../guide/journal.md) и сообщает о запусках по источнику (человек или авто), решениях gate по решению и причине, вмешательствах человека по запускам, результатах запуска и закрытых тикетах. Нечитаемые строки пропускаются и подсчитываются. `--mark-baseline` добавляет базовую точку; последующие отчёты охватывают только события после неё, если не указан `--all`. Пустой или отсутствующий журнал даёт нулевой отчёт и код 0.
- `emet usage [--session <id> | --file <path>] [--stalled [--minutes N]] [--project-dir <path>]`: сообщает об использовании сессии; `--stalled` выводит застрявших воркеров.
- `emet handoff --check <path> [--expect-skills a,b] | --render <path>`: проверяет или отображает заметку воркера `.emet/handoff-<ticket>.md`. Заметка может содержать раздел `skills:`, записанный как `skills: none` или `skills: loaded: a, b; missing: c`; он обязателен, только когда `state` равно `done`, а любое другое значение не проходит проверку. `--expect-skills a,b` (только для check) не пропускает проверку для каждого названного навыка, которого нет ни в списке `loaded`, ни в списке `missing`. Успешная проверка выводит `missing skills: …`, если список `missing` не пуст.
- `emet metrics [--run <id>]`: сообщает токены, стоимость в эквиваленте API и время выполнения по тикету, по волне и по запуску, считывая их из транскриптов сессий. Также сравнивает бюджет контекста, оценённый для каждого тикета, с фактически использованным каждым воркером. Его сводка помещается в конец итогового отчёта запуска.

### Планирование, ревью и посадка

- `emet promote --spec <id> [--dry-run] [--no-promote] [--hold]`: шаг after-spec согласно [`handoff.afterSpec`](configuration.md#handoff). В режиме `promote` открывает pull request из `develop` в `main` с заголовком `chore: 🔖 promote develop`, ждёт через `emet ci --pr <n> --wait`, сливает его merge-коммитом только при состоянии `pass`, а затем, только если `develop` отстаёт от `main`, открывает синхронизирующий pull request из `main` в `develop`, так же ждёт его проверок и сливает его merge-коммитом только при состоянии `pass`; синхронизирующий pull request в состоянии `fail`, `timeout` или `env-fault`, либо с отклонённым слиянием, остаётся открытым и никогда не меняет результат promote. Добавляет в журнал одно событие `promote` с номером pull request, `merged`, `syncPrNumber`, `syncMerged`, `syncReason`, `rule` и `reason`. `afterSpec` может быть списком правил; тогда режим выбирается по путям, которые принесло бы продвижение `develop` (см. [`handoff.afterSpec`](configuration.md#handoff)), а сбой `git fetch` или `git diff` приводит к завершению команды с кодом 1 до открытия какого-либо pull request. Выводимый результат содержит `rule` (индекс сработавшего правила, либо `null` для строковой формы или при отсутствии совпадения), `reason`, `syncPrNumber` (`null`, если синхронизирующий pull request не открывался), `syncMerged` и `syncReason` (фраза о том, почему синхронизирующий pull request остался открытым, иначе `null`) и `deployCheck: { run, reason }`, который сообщает, должен ли координатор запустить `emet deploy-check`. В режиме `release` ничего не сливает и оставляет release pull request человеку. При `afterSpec` `none`, с `--no-promote` или если последняя волна спецификации оставлена открытой или помечена, завершается с кодом 0 и пометкой `skipped`; тем не менее он выполняется после чистой последней волны, чтобы результат содержал решение `deployCheck` (на trunk `main` проверка деплоя выполняется независимо от режима). CI не в состоянии `pass` ничего не сливает и завершается с кодом 1. `--dry-run` не открывает pull request. `emet promote --spec <id> --hold` записывает маркер `<run dir>/runs/<id>/no-promote` и выводит `{"held":true}`; пока он существует, `emet promote --spec <id>` завершается с кодом 0 и пометкой `skipped`, не открывая pull request, поэтому `--no-promote` сохраняется между сессиями спецификации.
- `emet deploy-check [--json]`: запускает `deploy.check.command`, пока он не завершится с кодом 0, не более `retries` попыток или `timeoutSeconds` секунд, с паузой `intervalSeconds` между попытками, и выводит `state: ok | failed | timeout` с `attempts`. Код выхода `0` — ok, `1` — failed, `3` — timeout. Если `deploy.check` не настроен, завершается с кодом 0 и `skipped: "no deploy check configured"`. Координатор запускает его, только если в результате `emet promote` значение `deployCheck.run` равно true. См. [`deploy`](configuration.md#deploy).
- `emet validate --spec <id> | --file <path>`: проверка плана; см. [Гейты и записи](#гейты-и-записи).
- `emet surfaces --check <file.json | ->`: отклоняет пересекающиеся glob-шаблоны разрешённых поверхностей между тикетами волны.
- `emet approve --run <id>`, `emet materialize-log`, `emet results`, `emet verify`, `emet review-package`, `emet review`, `emet gate`: см. [Гейты и записи](#гейты-и-записи).
- `emet assess --base <ref> --head <ref>`: классифицирует diff как `passive`, `medium` или `high` и выводит JSON с уровнем, причинами и рекомендуемой моделью и усилием ревьюера, а также `browserVerify: { run, reason }`: `run` равно `true` только когда у уровня есть ревьюер, настроен [`verify.browser`](configuration.md#verify), бинарный файл `agent-browser` есть в PATH и, если задан `paths`, совпал изменённый путь; иначе `reason` называет первое невыполненное условие. Также печатает `dualReview: { run, reason }`: `run` равно `true` только когда уровень `high`, `agentHost` равен `claude`, [`review.dual`](configuration.md#review) не равен `off` и бинарный файл `codex` есть в PATH; иначе `reason` называет первое невыполненное условие. С `--quick` JSON дополнительно содержит `"quickRejected": true|false`, а команда завершается с кодом 1, когда уровень `high` (**Stop** для **Quick run**: без автослияния, PR остаётся открытым), и с 0 в остальных случаях; без `--quick` вывод и коды завершения не меняются. См. [Модели и усилие](../../README.md#models--effort) и [`review`](configuration.md#review).
- `emet land --spec <s> --branch <integration> --tickets <id,...>`: сливает интеграционную ветку в локальный trunk (`landing.mode` `merge`). `commands.selfCheck` заменяет CI, и ничего не отправляется.
- `emet spec-branch ensure|integrate|status|sync|land|abandon --spec <id>`: ветка спецификации `spec/<id>` режима `landing.unit: spec` (см. [`landing`](configuration.md#landing)). Все выводят JSON. `ensure` создаёт ветку из trunk (идемпотентно), записывает `.emet/specs/<id>/branch.json` и отказывает, если выбрана ветка другой спецификации. `integrate --wave <n> --branch <integration> --tickets a,b` сливает ветку волны в `spec/<id>` с `--no-ff` и трейлерами `Emet-Wave` и `Emet-Tickets`, записывает волну, добавляет `spec.integrate` и, когда `landing.pushSpecBranch` равен true, отправляет ветку без открытия PR. `status` выводит `branch`, `tip`, интегрированные волны и тикеты и `behindTrunk`, а когда волны не хватает, перестраивает `branch.json` по трейлерам. `sync` сливает trunk в ветку, никогда не делает rebase, а при конфликте прерывается, перечисляет пути и завершается с ненулевым кодом. `land [--partial]` выполняет синхронизацию, затем в режиме `pr` отправляет ветку, открывает один PR со строкой `Closes` на каждый тикет, ждёт его проверок и сливает через `landing.specMergeMethod` (по умолчанию merge-коммит, игнорируя `pr.mergeMethod`), а в режиме `merge` сливает в локальный trunk с `--no-ff` и никогда не отправляет изменения; добавляет `spec.land`. `abandon --force` помечает тегом `abandoned/spec-<id>`, удаляет ветку, добавляет `spec.abandon` и возвращает интегрированные тикеты локального трекера в `ready-for-agent`; без `--force` отказывает. `emet tracker frontier` считает тикеты из `branch.json` закрытыми блокерами, а `emet status` получает `specBranch` (`branch`, `tip`, `integratedWaves`).
- `emet spec-merge --spec <id>`: вливает дельты требований `ADDED`/`MODIFIED`/`REMOVED` спецификации в `docs/specs/<area>.md` (`specs.dir`). При включённом `specs.enabled` координатор пишет дельты и запускает команду один раз на спецификацию, в интеграционной ветке последней волны перед её ревью, а затем коммитит результат. `--deltas-dir` выводит каталог, в который кладутся дельты. Перед записью проверяет каждую область. Конфликт или требование, которое потеряло бы сценарий, завершается кодом 1 и оставляет все файлы нетронутыми. При выключенном `specs.enabled` ничего не вливает и завершается кодом 0.
- `emet map [--refresh]`: записывает обзор существующей кодовой базы (стек, структура, соглашения, тестирование, горячие точки) в `docs/agents/codebase.md` (`map.path`) с отметкой SHA коммита, по которому он построен. Один и тот же коммит всегда даёт один и тот же файл. `emet map --stale` завершается кодом 1, когда HEAD ушёл дальше отметки, и в этом случае `emet preflight` предупреждает. `emet map --for <globs>` выводит только разделы, соответствующие поверхностям правок тикета; этот вывод — единственная часть карты, входящая в задание воркера.
- `emet tracker create-spec|create-ticket|read|frontier|set-state|comment|close`: локальный трекер поверх `.scratch/`, JSON в stdout. См. [Локальный трекер](#локальный-трекер).
- `emet guard`: хук `PreToolUse` Claude Code; читает JSON хука из stdin (форма для Codex описана в разделе [Хост Codex](#хост-codex)). `emet self install` подключает его в `~/.claude/settings.json`. Блокирует несколько известных причин сбоев при запусках без присмотра (см. `emet/src/guard.ts`).

### Локальный трекер

При `tracker.kind: "local"` спецификации и тикеты — это markdown-файлы в `.scratch/` основного worktree (не под версионным контролем): `.scratch/<slug>/spec.md` и `.scratch/<slug>/issues/<NN>-<slug>.md`, каждый со строками `Status:` и `Blocked by:` и комментариями под `## Comments`. Координатор читает и записывает их через `emet tracker` (`create-spec`, `create-ticket`, `read`, `frontier`, `set-state`, `comment`, `close`). `emet init --tracker local` настраивает это. См. [ADR-0011](../adr/0011-local-tracker-scratch-convention.md).

`landing.mode` — это `"pr"` (по умолчанию) или `"merge"`, независимо от трекера. В режиме `merge` волна приземляется как одно локальное слияние в trunk командой `emet land`, при этом вместо CI выступает `commands.selfCheck`, а push не выполняется. При `landing.unit: "spec"` (по умолчанию) вся спецификация приземляется один раз через `emet spec-branch land`. `gh` нужен только если трекер — `github` или посадка выполняется через `pr`. См. [ADR-0010](../adr/0010-local-merge-landing.md) и [`landing`](configuration.md#landing).

### PR посадки и цепочки волн

При `landing.unit: "wave"` одна волна — один PR; при `"spec"` один PR охватывает все интегрированные волны. В его тексте для каждого тикета есть отдельная строка `Closes #N` (закрывающее ключевое слово трекера), а координатор переводит тикеты в in-review, когда открывает PR. Затем PR сливается согласно `pr.autoMerge` или остаётся открытым, если волна была помечена, `autoMerge` равен `false` или исправления CI закончились (тогда PR получает метку human-decision). Последующие волны выполняются в собственных сессиях, никогда не в той, что выполняла волну 1. Разделы `pr` и `handoff` управляют тем, что происходит дальше; см. [`pr`](configuration.md#pr) и [`handoff`](configuration.md#handoff).

`emet ci --pr <n> --wait [--rerun-flakes] [--timeout-minutes <m>]` опрашивает проверки PR, пока они не завершатся или не истечёт таймаут (по умолчанию 30). С `--rerun-flakes` каждая упавшая проверка один раз перезапускается через `gh run rerun --failed`; проверка, прошедшая при перезапуске, считается Flake. Выводит `state: pass | fail | env-fault | timeout`, упавшие проверки и `flakeReruns` и никогда не сливает. PR без проверок — это `pass` с `noChecks: true`. Код `0` — pass, `1` — fail или env-fault, `3` — timeout. `env-fault` означает проверки, завершившиеся `STARTUP_FAILURE` или слишком долго стоявшие в очереди: CI, который так и не запустился, а не сбой кода.

При `tracker.kind: "github"` `emet tracker close <ticket>... [--pr <n>]` закрывает каждый тикет (`CLA-<n>`, `#<n>` или просто число) через `gh issue close --reason completed`, проверяет его состояние и сообщает `closed` или `already-closed`. `--pr` добавляет комментарий "Landed in #<n>". После обработки тикетов читает родительский спек-issue каждого закрытого тикета (`gh issue view <n> --json parent`) и, когда `subIssuesSummary` показывает, что все подзадачи завершены, закрывает этот спек как выполненный с комментарием "All <total> tickets landed." и сообщает о нём в `specs` как `closed`, `open`, `already-closed` или `failed`; сбой при чтении или закрытии спека также приводит к выходу с кодом `1`. Если какой-то тикет не удалось закрыть, завершается с кодом `1` после обработки остальных. Тикеты Linear координатор подтверждает как Done через Linear MCP.

### Хост Codex

Эти команды обслуживают хост агента Codex (`agentHost` `"codex"`); см. [руководство по Codex](../guide/codex.md).

- `emet dispatch --role worker --run <id> --ticket <id> --prompt-file <file> [--model <m>] [--effort <e>] [--root <dir>]`: после проверки резервирования и слота создаёт `.emet/worktrees/agent-<ticket>`, собирает оверлей `CODEX_HOME` для запуска и стартует воркера как отдельный `codex exec`. `emet dispatch --wait --run <id> --ticket <id> [--timeout <s>]` ждёт завершения и печатает записанный статус результата.
- `emet review-run --run <id> --ticket <id> --package <file> --tier <medium|high|passive> [--browser-verify true|false]`: запускает ревьюера как `codex exec` только для чтения над пакетом из `emet review-package` и печатает JSON замечаний для `emet review --findings`. Уровень `passive` не запускает процесс. `--browser-verify` по умолчанию `false`; при `true` промпт заканчивается осью Browser, где `--session review-<run>` подставляется из `--run`, так что ревьюер Codex проверяет UI так же, как ревьюер Claude (передавайте его, когда `emet assess` напечатал `browserVerify.run: true`; см. [`verify`](configuration.md#verify)). Без флага промпт не меняется, а значение, отличное от `true` и `false`, завершается с кодом 2 и строкой использования. `--coverage-out <file>` дополнительно записывает Coverage verdicts ревьюера Codex в `<file>` как JSON-массив (stdout по-прежнему печатает только замечания); используйте его на хосте Codex, где работает один ревьюер. Замечания могут содержать необязательные поля `s` и `userOption`, описанные в `emet review`.
- `emet launch <spec-id> --wave <n>`: на этом хосте запускает отдельный `codex exec` с `$emet:run --dispatch <spec>` и записывает id его треда. Вкладка Orca не открывается, а `codex exec resume <id>` продолжает сессию.
- `emet guard`: при `EMET_AGENT_HOST=codex` читает вход хуков Codex, сверяет пути `apply_patch` с `.emet/surface.json` и держит шлюз одобрения закрытым, пока не придёт строка промпта `approve <id>`.

Фазы сами не решают, когда тикет готов, пригоден к слиянию или заслуживает повторной попытки. Они вызывают команду CLI, которая читает запись на диске и выводит решение. ## Коды завершения

Коды завершения имеют одинаковый смысл во всех подкомандах.

| Код | Значение                                                                                                  |
| --- | --------------------------------------------------------------------------------------------------------- |
| `0` | Чисто.                                                                                                    |
| `1` | Есть замечания, требующие действий.                                                                       |
| `2` | Ошибка конфигурации или использования; инструмент на самом деле не запускался. Также неизвестная команда. |
| `3` | Внутренняя ошибка.                                                                                        |

Неизвестный флаг тоже завершается с кодом `2` и называет флаг. Ctrl-C завершается с кодом `130`.

## Глобальные флаги

Их принимает каждая команда; собственные флаги каждой команды перечисляет `emet <command> --help`.

| Флаг         | Действие                                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| `--json`     | Выводит в stdout один конверт `{ok, data, error: {code, message, fix}}`, в том числе для `--help` и `--version`. |
| `--no-color` | Отключает цвет ANSI. Цвет также учитывает `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb` и то, является ли вывод TTY.    |
| `--verbose`  | Выводит стек неожиданной ошибки. Без него перехватчик верхнего уровня выводит однострочную ошибку.               |
| `--help`     | Выводит справку по использованию команды.                                                                        |

`emet --version` выводит версию; `emet --version --json` выводит `{"ok": true, "data": {"version": ...}, "error": null}`. При `--json` упавшая команда завершается со своим обычным кодом и выводит `ok: false` с `code` ошибки `findings`, `usage`, `internal`, `slice-timeout`, `expired`, `bad-range` или `exit-<n>`; то, что команда вывела в stdout, становится `data` конверта.

В TTY `emet` выводит в stderr однострочное уведомление, если известен более новый релиз. Проверка выполняется не чаще раза в сутки, ответ кэшируется, ожидания сети нет, а при `--json` или без TTY уведомление не выводится.

## Переменные окружения

Переменные для пользователей. Заданная переменная переопределяет соответствующее значение конфигурации.

| Переменная                    | Действие                                                                                                                                                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `EMET_SKIP_DEPENDENCY_CHECKS` | `EMET_SKIP_DEPENDENCY_CHECKS=1 emet preflight` понижает блокировку по зависимостям до предупреждения для этого одного запуска. Задавайте её в собственной оболочке, а не в том, что координатор запускает без присмотра. |
| `EMET_MAX_LIVE_WORKERS`       | Переопределяет [`concurrency.maxLiveWorkers`](configuration.md#concurrency); принимает положительное целое или `auto`.                                                                                                   |
| `EMET_RUN_IDLE_THRESHOLD_MS`  | Переопределяет [`concurrency.runIdleThresholdMs`](configuration.md#concurrency), в миллисекундах.                                                                                                                        |
| `EMET_STATE_DIR`              | Общий каталог состояния хоста, в котором хранится пул слотов воркеров. Порядок определения: `$EMET_STATE_DIR`, затем `$XDG_STATE_HOME/emet`, затем `~/.local/state/emet`.                                                |
| `EMET_MEM_RESERVE_GIB`        | Запас памяти в GiB, который должен оставаться свободным; захват слота отклоняется, если доступной памяти меньше. По умолчанию 8. Также влияет на предел воркеров `auto`.                                                 |
| `EMET_MEM_PER_WORKER_GIB`     | Память в GiB, принимаемая на одного воркера, когда `maxLiveWorkers` равен `auto`. По умолчанию 2. Увеличьте для более тяжёлого стека на воркера, например E2E-набора с браузером на каждый worktree.                     |
| `EMET_CPU_OVERSUBSCRIBE`      | Множитель CPU для предела воркеров `auto`. По умолчанию 1.                                                                                                                                                               |
| `EMET_AUTO_UPDATE`            | `EMET_AUTO_UPDATE=0` отключает `emet self update --auto`: команда завершается с кодом 0 без обращения к сети. То же, что `emet self update --auto off`.                                                                  |
| `EMET_AGENT_HOST`             | `codex` заставляет `emet guard` читать вход хуков Codex. Задаётся хуками Codex; в Claude Code оставьте незаданной.                                                                                                       |

Предел `auto` равен `clamp(min(cpuCount × EMET_CPU_OVERSUBSCRIBE, floor((memTotal − EMET_MEM_RESERVE_GIB) / EMET_MEM_PER_WORKER_GIB)), min, max)`. Устаревшие имена `FORGE_*` по-прежнему читаются; при наличии обоих приоритет у `EMET_*`.
