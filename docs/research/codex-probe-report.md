# Codex probe report

The real-Codex check of every `unverified` point in [Running emet on Codex](../guide/codex.md), made by `tools/codex-probe.ts` (`EMET_CODEX_PROBE=1 bun run probe:codex -- --flow`). Terms follow [GLOSSARY.md](../../GLOSSARY.md). Background: [the viability research](codex-viability.md).

Re-run on 2026-11-09 and 2026-11-10 (spec #376), after the fixes of its wave 1: the `danger-full-access` worker default with the `emet guard` push denial, the generated overlay `config.toml`, the registered Codex Agent host, model resolution from the real models cache, and the thread-id worker identity. The run used `codex-cli 0.167.0`, signed in with a ChatGPT free plan, on Linux. Every model run used effort `low` and the cheapest resolved model (`gpt-6-luna`), with a 15 minute cap. Each run used a throwaway repo under `/tmp` with no remote. No run hit a plan limit, so no row is `blocked-by-plan-limit`. The first report (spec #370) had five `failed` rows; all five are `verified` now.

Verdicts: `verified` (the behaviour holds), `failed` (it does not, or the evidence cannot show it), `blocked-by-plan-limit` (a rate or usage limit answered twice), `not-applicable`. The probe retries a plan-limit answer once in every model step, including flow wave 1, `emet launch` and the inner run of nested dispatch, so a plan limit is never reported as `failed`.

Two waves therefore landed real commits by Codex workers on `develop`: `feat: add a` (wave 1, `emet dispatch`) and `12faa85` (wave 2, from the launched `$emet:run`).

The flow needed four probe-side fixes before `$emet:run` would dispatch wave 2, each a gap between the probe's throwaway repo and a repo set up by a real run: the `TODO(emet):` scaffold markers of `emet init` (preflight refuses them), the missing approval record, a spec without `## Specs` items and a plan without `covers` (the approval gate validates the plan), and ticket bodies without `## Allowed edit surfaces`. The launched session loaded the skill from the overlay's plugin cache (`plugins/cache/emet-marketplace/emet/0.4.0/codex/skills/run/references/…`) each time.

## Follow-ups

- `emet init` writes Claude model names (`sonnet`, `opus`, `haiku`) into `models` even when `agentHost` is `codex`. A launched `$emet:run` passes `models.worker.model` as `emet dispatch --model sonnet`, and `dispatch` sends an explicit `--model` to Codex unresolved, so the worker dies with "The 'sonnet' model is not supported when using Codex with a ChatGPT account" (flow run 4). Resolve an explicit `--model` through `resolveCodexModel` too, and have `emet init` write Codex models for `agentHost: "codex"`. The probe sets `models` itself.
- `emet lock-reason` with no `--anchor` looks for an ancestor whose comm is `claude` (`resolveAnchorPid` with the Claude host's `anchorProcessName`), even when `agentHost` is `codex`: "no ancestor of pid … has comm \"claude\" within 32 hops". In flow run 5 the coordinator passed `--anchor <session pid>` itself; in flow run 6 it gave up and left ticket 02 `ready-for-agent`. Resolve the anchor through the configured Agent host.
- Flow run 7 stopped at `emet slots --acquire`: the host's memory brake (8.0 GiB available, 8.0 GiB reserve) refused a slot because other sessions were using this machine's memory. Not a Codex issue, but the probe flow should run on a quiet host.
- After the `sonnet` worker failed (flow run 4), the coordinator's second `emet dispatch` for the same ticket stopped with `worktree already exists`. Give `emet dispatch` a way to re-dispatch a ticket whose earlier worker died.
- A Codex worker wrote its handoff note without the required sections, and the coordinator fixed it before `emet verify` passed (flow run 5). Check that the worker prompt's handoff instructions survive the Codex skill build.
- `emet metrics` reports no `tickets.json` for a launched wave-2 run: the plan lives in the spec's approval run (`spec<id>`), not in the wave's run directory.
- Unattended supervision under systemd units or containers was not exercised.

## Manual check

Run these on a throwaway repo in a terminal with `codex` signed in and an `emet` CLI built from `develop`. Report back the item named in each step.

1. `mkdir /tmp/emet-manual && cd /tmp/emet-manual && git init -b develop && git commit --allow-empty -m init`. Expected: `git log --oneline` prints one line. Report: that line.
2. `emet --help | grep -E 'dispatch|review-run'`. Expected: two lines, one per command (an `emet` 0.4.0 prints none). Report: the lines, or "none".
3. `codex plugin marketplace add andryorelabs/emet && codex plugin add emet@emet-marketplace && codex plugin list | grep emet@`. Expected: `emet@emet-marketplace  installed, enabled`. Report: that line.
4. `emet init --tracker local`, then set `"agentHost": "codex"`, `repo.trunk` to `develop` and every `models` entry to a Codex model your plan lists in `emet.config.json`, and `emet preflight`. Expected: preflight does not fail with `unknown agent host`. Report: the exit code and, if it fails, its last line.
5. Start `codex` in the repo and send `$emet:run add hello.txt containing hello`. Expected: the reply follows the skill's Phase 0 and asks interview questions; it does not run `emet run`. Report: the first line of the reply.
6. Answer until the plan is shown, then run `ls .emet/runs` in another terminal. Expected: a `spec<id>` directory with no `approval.json`. Report: the `<id>`.
7. In Codex, send `create test.txt now`. Expected: the tool call is denied with `not approved: send approve <id>` and `test.txt` does not exist. Report: the denial text.
8. Send the prompt line `approve <id>` exactly. Expected: `.emet/runs/spec<id>/approval.json` exists. Report: `ls .emet/runs/spec<id>`.
9. Let wave 1 run, then `git -C .emet/worktrees/agent-<ticket> log --oneline -2`. Expected: a ticket commit above `init`. Report: the output.
10. `sha256sum ~/.codex/config.toml` before step 5 and after step 9. Expected: the same hash, unless you accepted a trust prompt for this directory in step 5 (Codex records that itself). Report: both hashes and whether you accepted the prompt.
